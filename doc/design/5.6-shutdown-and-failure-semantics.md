# 5.6 Shutdown and Failure Semantics

[Architecture documentation](README.md) >
[5. VM Lifecycle and State](5-vm-lifecycle-and-state.md)

Orderly guest shutdown carries the workload status through the platform
shutdown device. The VMM stops virtual processors and devices, drains the
bounded final output path, releases attachments, and reports completion only
after teardown reaches a known state.

## 5.6.1 Final Output and Exit Status

Guest-requested exit drains the byte channel and, when present, its host
output relay before reporting completion, within one combined five-second
deadline. Success preserves the guest's exit status; an endpoint, relay, or
timeout failure becomes a process-exit error instead of silently discarding
final output. This guarantee covers the byte channel and its relay, not every
console endpoint. Under the management RPC, a zero guest status completes a
pending wait and stops the server cleanly, while a nonzero status or a failed
drain fails the wait and ends the server with an error. After teardown, the
VMM can write the bounded
[outcome report](1.4-trust-boundaries.md#145-host-facing-outputs).

As Table 5.8 shows, the guest reports its own fail-fast conditions through
exit statuses, each after a violation event or an error line that names the
cause.

**Table 5.8.** Guest fail-fast exit statuses.

| Status | Cause |
| ---: | --- |
| 193 | A time ABI conformance check failed |
| 194 | The violation watcher detected a runtime clock violation |
| 195 | The time ABI's part of post-restore repair failed |
| 125 | Sandbox setup, such as share placement, failed before the workload started |
| 1 | Another snapshot or restore step of the guest agents failed, such as processor activation or the identity refresh |

A status alone does not identify the cause. In a one-shot lifecycle, the
guest's exit status is otherwise the workload's, which can take any 8-bit
value, and status 1 is also the guest's generic failure status. A host
therefore identifies a fail-fast condition by its status together with the
violation event or error line that precedes it. Statuses in the control
protocol's exit reports and errors, such as 125 for an exceeded output limit,
travel with their own categories instead, as
[Host-Guest Control Interface](4.4-host-guest-control-interface.md#441-operations)
describes.

## 5.6.2 Failure Classes

Failures are classified by whether execution can safely continue:

- Invalid configuration, artifacts, or attachments fail before guest entry,
  except an activation record, which the guest agents validate during repair.
- Time-contract violations reject a cold boot, capture, or restore with a
  stable error code and never fall back.
- A rejected capture preflight may return the still-consistent source to
  execution.
- A capture failure after virtual-processor stopping begins is terminal unless
  rollback is proven complete.
- A failure after snapshot publication never resumes the source.
- A post-restore repair failure before the acknowledgement, or a missing
  acknowledgement, leaves input gated and terminates the restored process.
- A platform-clone activation failure after the acknowledgement powers off
  the guest before it reports readiness, so no workload runs in a partially
  activated clone.
- Malformed saved state or failed attachment reconstruction prevents any
  restored virtual processor from running.

This fail-closed rule prevents success-shaped recovery from uncertain state.
The architecture prefers terminating one process generation over resuming a
guest whose device ownership, external input, persisted artifacts, or
execution boundary can no longer be established.
