# 5.6 Shutdown and Failure Semantics

[Architecture documentation](README.md) >
[5. VM Lifecycle and State](5-vm-lifecycle-and-state.md)

Orderly guest shutdown carries the workload status through the platform
shutdown device. The VMM stops virtual processors and devices, drains the
bounded final output path, releases attachments, and reports completion only
after teardown reaches a known state.

## 5.6.1 Final Output and Exit Status

Guest-requested exit drains the byte channel and, when present, its host
output relay before reporting completion, and writes the output that a
[boot console](3.3-consoles.md#331-boot-console) on the host's standard
streams accepted, within one combined five-second deadline. Success preserves
the guest's exit status; an endpoint, relay, or timeout failure becomes a
process-exit error instead of silently discarding final output. This guarantee
covers the byte channel, its relay, and the boot console on the standard
streams, not every console endpoint. Under the management RPC, a zero guest
status completes a pending wait and stops the server cleanly, while a nonzero
status or a failed drain fails the wait and ends the server with an error.
After teardown, the VMM can write the bounded
[outcome report](1.4-trust-boundaries.md#145-host-facing-outputs), which `nvx`
reads for its caller: `vm::stop` returns that read beside its confirmation of
the VM's exit, so that a report that cannot be read never hides a confirmed
exit.

As Table 5.9 shows, the guest reports its own fail-fast conditions through
exit statuses, each after a violation event or an error line that names the
cause.

**Table 5.9.** Guest fail-fast exit statuses.

| Status | Cause |
| ---: | --- |
| 193 | A time ABI conformance check failed |
| 194 | The violation watcher detected a runtime clock violation |
| 195 | The time ABI's part of post-restore repair failed |
| 125 | Sandbox setup, such as share placement, failed before the workload started |
| 1 | Another snapshot or restore step of NVX's guest snapshot tool failed, such as processor activation or the identity refresh |
| 40 to 45 | Another step of a platform clone's repair failed, one status for each class: the restore itself, the processor target, the memory target, the memory's activation, the reseed, and the restore's finish |
| 50 to 58 | A platform clone's activation failed, one status for each class: its deadline, the host's session, the record, the resources that the record expects, the root, the workload, the host export, the network settings, and the init's own order |

A status alone does not identify the cause. In a one-shot lifecycle, the
guest's exit status is otherwise the workload's, which can take any 8-bit
value, and status 1 is also the guest's generic failure status. A host
therefore identifies a fail-fast condition by its status together with the
violation event or error line that precedes it. Statuses in the control
protocol's exit reports and errors, such as 124 for an execution that timed
out, travel with their own categories instead, as
[Host-Guest Control Interface](4.4-host-guest-control-interface.md#441-operations)
describes.

The statuses of a clone's repair and activation, and the time ABI's, are
public contracts of `nvx`, in its `protocol::status`. `guest::snapshot::capture`
returns a repair's as the status with which the guest must end, and an init
ends a failed activation with the status of its class. When a restore ends
before Ready, `RestoreMachine` attributes it by the status in the outcome
report that its caller reads: to the guest's repair or time ABI, to the
restore's request, or to nothing that the evidence establishes.

## 5.6.2 Failure Classes

Failures are classified by whether execution can safely continue:

- Invalid configuration, artifacts, or attachments fail before guest entry.
- Time-contract violations reject a cold boot, capture, or restore with a
  stable error code and never fall back.
- A rejected capture preflight may return the still-consistent source to
  execution.
- A capture failure after virtual-processor stopping begins is terminal unless
  rollback is proven complete.
- A failure after snapshot publication never resumes the source.
- A post-restore repair failure before the acknowledgement, or a missing
  acknowledgement, leaves input gated and terminates the restored process.
- Malformed saved state or failed attachment reconstruction prevents any
  restored virtual processor from running.

This fail-closed rule prevents success-shaped recovery from uncertain state.
The architecture prefers terminating one process generation over resuming a
guest whose device ownership, external input, persisted artifacts, or
execution boundary can no longer be established.

`nvx` fails closed the same way, and reports each refusal or failure with an
error whose kind its caller acts on, `ErrorKind`: for example, `Unsupported`
for a configuration or a restore that it refuses, `Unavailable` for a
snapshot whose time contract the host cannot meet now, `Exited` for a VM that
ended, `StillRunning` for an exit that it could not confirm, and
`RuntimeMismatch` for a VM of another runtime identity. A failed restore, a
`RestoreError`, keeps its phase, its evidence, what that evidence attributes
it to, and whether guest code may have run, and neither stops the VM nor
records anything: the caller decides whether to stop the VM, retry, or set the
snapshot aside.
