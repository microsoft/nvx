# 4.1 Guest Filesystem and Image Model

[Architecture documentation](README.md) >
[4. Guest Runtime Architecture](4-guest-runtime-architecture.md)

As Table 4.1 shows, the guest agents run workloads in one of two roots.

**Table 4.1.** Workload roots.

| Root | Construction | Host content |
| --- | --- | --- |
| Layered sandbox root | An overlay of one read-only image layer and a private writable upper, on scratch or in guest memory | Live host shares bound at declared targets |
| Blockless managed root | The guest's own initramfs root, without block devices | Host directories bound by a host mapping table |

The guest kernel provides the facilities both roots need: virtio-blk,
virtio-fs, EROFS with compression and extended attributes, tmpfs with
extended attributes, overlayfs, cgroup v2 with the memory and process
controllers, namespaces, BPF system calls, and cgroup BPF programs.

## 4.1.1 Layered Sandbox Root

As Figure 4.1 shows, the layered root combines one immutable EROFS `distro`
layer with one private writable upper: either an ext4 scratch device or a
tmpfs in guest memory.

```text
/run/nvx/layers/distro   (EROFS) ----------> lower directory
/run/nvx/scratch/upper   (ext4) -----------> upper directory
  or /run/nvx/tmpfs/upper (tmpfs)
/run/nvx/scratch/work    (same ext4) ------> work directory
  or /run/nvx/tmpfs/work (same tmpfs)
                                          overlay --> /run/nvx/rootfs
one-shot: virtio-fs tag microvm (optional share) ---> /run/nvx/rootfs/TARGET
  or an aggregate        ---> /run/nvx/shares, each child bound at
                              /run/nvx/rootfs/TARGET
managed: the aggregate export ---> /run/nvx/hostfs/root, each mapping of the
                              table mounted at /run/nvx/rootfs/TARGET
```

**Figure 4.1.** Layered sandbox root assembly.

The `distro` layer is required and holds a curated base operating system. One
immutable layer file can serve many sandboxes, and compressed EROFS reduces
stored and cached image bytes, because the guest kernel decompresses blocks as
it reads them. No FUSE daemon or in-guest fetch service is involved in the root
filesystem.

The launcher describes the root to the guest in two boot tokens, whose grammar
one contract module defines, with the host's renderer and a parser for guests:

- `nvx_layer=distro,0xd0003000,FORMAT[:IDENTITY]` names the image on the
  `distro` block device: its format, `erofs` for an EROFS filesystem or `gpt`
  for a GPT disk, and the identity that the guest expects of it, if any, the
  filesystem UUID or the disk GUID in canonical lowercase text. No token names
  a partition GUID.
- `nvx_scratch=0xd0006000,ext4` keeps the overlay's upper on the whole-device
  ext4 `scratch` disk, and `nvx_overlay_upper=ramfs` keeps it in guest
  memory, on a tmpfs, with no `scratch` block device.

Guests refuse a token without a value, a repeated token, both uppers, an image
without an upper or an upper without an image, a RAM upper beside a `scratch`
block device, and every other form, including the earlier `nvx_layer` form
without a format, rather than probe the devices. The guest agents described
here assemble only an EROFS image, over either upper: they refuse a GPT image
with a message that says so.

The guest agents assemble the root in this order:

1. Mount runtime tmpfs and cgroup v2, create sibling guest-agent and
   container cgroups, and move the guest agents into the guest-agent cgroup.
2. Read the root's boot tokens, and resolve each role's MMIO address through
   the kernel's platform-device resources rather than assuming a device name
   or enumeration order. For a RAM upper, refuse any device at the `scratch`
   role's address.
3. Check any expected sector count, flush cached block-device buffers, mount
   the `distro` layer read-only as EROFS, and check its filesystem UUID when
   the token names one.
4. Mount the upper's file system, and create the overlay's upper and work
   directories on it: resolve and flush scratch and mount it as ext4 with
   `rw,nosuid,nodev`, or mount a tmpfs with `mode=0755,nosuid,nodev` at the
   kernel's default size, half of the guest's RAM.
5. Mount the overlay with the `distro` layer as its lower directory,
   metadata-only copy-up, and extended inode numbers.
6. Verify the workload identity in the assembled root, mount each live share
   of a one-shot sandbox at its target inside that root, or the host's export
   of a managed sandbox, and write the workload's machine ID to a runtime
   file.
7. Start the workload behind a barrier and place it in the workload cgroup
   before releasing it; a managed sandbox's agent first maps the shares from
   the export, as their mapping table orders.
8. Wait for the workload, unmount the shares in reverse order and then the
   overlay, the `distro` layer, and the upper, and report the workload's
   status.

The UUID check detects attachment mistakes; it is not a content-integrity
proof, and neither the guest nor the VMM verifies layer contents.
Metadata-only copy-up interprets overlay metadata stored in the `distro`
layer, so that layer is a trusted input that must not carry untrusted overlay
attributes. A metadata-only change avoids copying file contents, but a data
write still copies the whole lower file into the upper, so the upper's
capacity must account for copy-up. The two uppers spend different resources:

- Scratch consumes host storage rather than guest RAM, can run out of space
  independently of guest memory pressure, and keeps a managed sandbox's
  changes from one start to the next.
- A RAM upper consumes guest memory. The memory cgroup of the process that
  writes a page, normally the workload's, is charged for it, so the
  workload's memory limit also bounds its files, and since the guest has no
  swap, those pages stay resident until their files are removed. A write
  beyond the tmpfs size fails with `ENOSPC`, and nothing the workload writes
  outlives the virtual machine.

The initramfs remains the guest agents' root; it is not another workload
layer. A RAM upper uses the machine's RAM-backed overlay layout, which has
exactly one read-only `distro` block and no scratch, and which supports
neither capture nor restore; see
[Storage Configuration](2.1-machine-model-and-configuration.md#213-storage-configuration).

## 4.1.2 Live Host Shares

A live share exposes a host directory, such as a source checkout or a tool
cache, or a single host file, such as a settings file, to the workload without
copying it into an image: edits are visible on both sides without staging or
copy-back.

One shared directory attaches as a directory export. Several shares, or any
shared file, attach as an aggregate whose children are independent volumes
with their own access modes and policies; see
[Host Filesystem](3.6-host-filesystem.md). Each child is named
after its index and a digest of its guest target, so a snapshot pins every
target, and a restore that requests another target fails before the guest
runs. Before launch, the launcher rejects policy paths outside their share or
on a shared file, guest targets or host paths that equal or contain one
another, and one-shot shares whose boot tokens exceed the command-line budget.

A one-shot sandbox receives its shares at boot. The machine profile announces
the export through its host filesystem tokens, and the launcher adds one share
token per child that names the child, its guest target, its mode, and whether
it is a file. The guest agents then:

- Parse every share token and create every target before mounting anything,
  so a malformed bootstrap mounts nothing.
- Create each target inside the workload root one component at a time and
  refuse a path that crosses a symbolic link, so an image layer cannot
  redirect a share outside the root.
- Create a regular file as the last component of a file target and a
  directory for any other target.
- Refuse repeated children, overlapping targets, and targets that the
  runtime later binds over, such as the machine ID file.
- Mount a single share at its target with its mode and `nosuid,nodev`.
- Mount an aggregate at a root-only location outside the workload root and
  bind each child at its target with its mode and `nosuid,nodev`.

The workload's mount namespace inherits these mounts, and teardown unmounts
the binds in reverse order before the aggregate. Any refusal or mount failure
aborts the sandbox instead of starting the workload without its shares.

A managed sandbox records its shares when it is provisioned, and on every
start receives them as the blockless root receives its host directories (see
4.1.3): the host exports every share as a numbered child of one aggregate,
which the guest agents mount at the same root-only location, and delivers the
mapping table once the managed agent is ready. The agent maps each entry
beneath the assembled root, whose own mount is the overlay, and refuses the
targets that the container runtime keeps, as the boot tokens' targets are
refused. A mapping that fails ends the start, after the guest shuts down as
stop has it do: it unmounts the mappings in reverse order before the export
and the overlay.

## 4.1.3 Blockless Managed Root

Without image layers, each workload runs directly in the guest's initramfs
root, inside a dedicated execution cgroup. Host directories reach it through a
host mapping table rather than an image:

- The host exports the outermost mapped directories, and each mapped file
  outside them on its own, as numbered children of one aggregate, so a file
  child exposes only its file. The guest agents mount the aggregate at a
  root-only location before they accept control traffic.
- The host enforces each mapping's access itself: a child is read-write only
  if it holds a read-write mapping, and writes are limited to read-write
  mappings. A whole volume is never mapped, and a mapping table that would
  need more children than an aggregate holds is refused rather than exported
  through the directories of its files, which would expose more than the
  files.
- The kernel command line announces the number of mappings, and the host
  delivers the table over the
  [control interface](4.4-host-guest-control-interface.md). The guest agents accept
  entries only in order and up to the announced count, and validate each request
  before mounting anything. They walk to each target beneath the descriptor of
  their root, a mount of a whole file system rather than a bind of a directory,
  through no symbolic or magic link, create what it lacks only on the root's own
  mounts, never inside another mapping, and attach a copy of the source's mount
  there with `nosuid,nodev`, read-only when requested, set before the mapping is
  visible. They refuse to run workloads until every announced mapping is
  mounted, and a failed mapping keeps them refusing.
