# 4.1 Guest Filesystem and Image Model

[Architecture documentation](README.md) >
[4. Guest Runtime Architecture](4-guest-runtime-architecture.md)

As Table 4.1 shows, the guest agents run workloads in one of two roots.

**Table 4.1.** Workload roots.

| Root | Construction | Host content |
| --- | --- | --- |
| Layered sandbox root | An overlay of a read-only image and a private writable upper layer on scratch or in guest RAM | Live host shares bound at declared targets, or, in a managed lifecycle, host directories bound by a host mapping table |
| Blockless managed root | The guest's own initramfs root, without block devices | Host directories bound by a host mapping table |

The guest kernel provides the facilities both roots need: virtio-blk,
virtio-fs, EROFS with compression and extended attributes, ext4, GPT partition
tables, overlayfs, cgroup v2 with the memory and process controllers,
namespaces, BPF system calls, and cgroup BPF programs.

## 4.1.1 Layered Sandbox Root

As Figure 4.1 shows for an EROFS image with its upper layer on scratch, the
layered root combines the immutable `distro` image with one private writable
upper layer. The image is either one EROFS filesystem or a GPT disk whose
first partition holds image metadata, such as the image's configuration, and
whose later partitions hold read-only ext4 lower layers, ordered from base to
top. The upper layer is on an ext4 scratch device or, in the RAM-backed
overlay layout, in guest RAM.

```text
/run/nvx/layers/distro   (EROFS) ----------> lower directory
/run/nvx/scratch/upper   (ext4) -----------> upper directory
/run/nvx/scratch/work    (same ext4) ------> work directory
                                          overlay --> /run/nvx/rootfs
virtio-fs tag microvm    (optional share) ---> /run/nvx/rootfs/TARGET
  or an aggregate        ---> /run/nvx/shares, each child bound at
                              /run/nvx/rootfs/TARGET
```

**Figure 4.1.** Layered sandbox root assembly.

The `distro` layer is required and holds a curated base operating system. One
immutable layer file can serve many sandboxes, and compressed EROFS reduces
stored and cached image bytes, because the guest kernel decompresses blocks as
it reads them. No FUSE daemon or in-guest fetch service is involved in the root
filesystem.

The guest agents assemble the root in this order:

1. Mount runtime tmpfs and cgroup v2, create sibling guest-agent and
   container cgroups, and move the guest agents into the guest-agent cgroup.
2. Resolve each role's MMIO address through the kernel's platform-device
   resources rather than assuming a device name or enumeration order.
3. Check any expected sector count and flush cached block-device buffers.
   Mount an EROFS image read-only and check any expected filesystem UUID. For
   a GPT image, validate only the primary header and entry array, reread the
   partition table, and mount partitions 2 through N as read-only ext4 lower
   layers with `ro,nosuid,nodev`. Never use the backup header and never add
   `noload`.
4. Resolve and flush scratch, mount it as ext4 with `rw,nosuid,nodev`, and
   create its upper and work directories, or, in the RAM-backed overlay
   layout, create them in tmpfs mounted with `nosuid,nodev` at the kernel's
   default size, half of guest memory.
5. Mount the overlay with the EROFS image, or the GPT image's layers from top
   to base, as its lower directories. Every image uses
   `metacopy=on,xino=on` by default. An orchestrator whose lower layers may
   carry untrusted overlay attributes selects
   `metacopy=off,redirect_dir=nofollow`. The guest uses exactly the selected
   option set without fallback and mounts the merged root `nosuid,nodev`.
6. Verify the workload identity in the assembled root, mount each live share
   at its target inside that root, and, when selected, write the generated
   machine ID to a runtime file.
7. Start the workload behind a barrier and place it in the workload cgroup
   before releasing it.
8. Wait for the workload, unmount the shares in reverse order and then the
   overlay, the `distro` image's mounts, and scratch or tmpfs,
   and report the workload's status.

GPT validation bounds the header and entry array, verifies their CRCs,
extents, indices, and GUIDs, and permits at most 255 used partitions, the
kernel's limit. The primary header's alternate LBA must lie inside the device,
which may present zeros past a shorter image. Partition 1 holds opaque
metadata bytes. The guest reads them up to a caller-selected bound, trims
trailing NUL and whitespace, and never probes the partition as a filesystem;
the adapter parses the result. After the partition-table reread, every kernel
partition must match its validated entry.

Expected identities are optional inputs: the EROFS filesystem UUID, or the
GPT disk GUID, partition GUIDs, and partition sizes. NVX's adapter passes the
EROFS UUID or GPT disk GUID from its boot token. These checks detect attachment
mistakes; they are not a content-integrity proof, and neither the guest nor
the VMM verifies layer contents. Metadata-only copy-up interprets overlay
metadata stored in the `distro` layer, so an orchestrator selects the
non-metacopy option set when lower layers may carry untrusted overlay
attributes. A metadata-only change avoids copying file contents, but a data
write still copies the whole lower file into the upper layer, whose capacity
must account for copy-up. Scratch consumes host storage rather than guest RAM
and can run out of space independently of guest memory pressure.

The initramfs remains the guest agents' root; it is not another workload
layer. The guest agents keep the overlay upper layer on scratch or, when the
machine declares the RAM-backed overlay layout, which has no scratch, in guest
RAM, where the workload's writes consume guest memory instead of host
storage.

## 4.1.2 Live Host Shares

A live share exposes a host directory, such as a source checkout or a tool
cache, or a single host file, such as a settings file, to the workload without
copying it into an image: edits are visible on both sides without staging or
copy-back.

One shared directory attaches as a directory export. Several shares, or any
shared file, attach as an aggregate whose children are independent volumes
with their own access modes and policies; see
[Host Filesystem](3.6-host-filesystem.md). Each child is named
after its index and a digest of its guest target, so a snapshot pins every
target, and a restore that requests another target fails before the guest
runs. Before launch, the launcher rejects policy paths outside their share or
on a shared file, guest targets or host paths that equal or contain one
another, and shares whose boot tokens exceed the command-line budget.

The machine profile announces the export through its host filesystem tokens,
and the launcher adds one share token per child that names the child, its
guest target, its mode, and whether it is a file. The guest agents then:

- Parse every share token and create every target before mounting anything,
  so a malformed bootstrap mounts nothing.
- Create each target inside the workload root one component at a time and
  refuse a path that crosses a symbolic link, so an image layer cannot
  redirect a share outside the root.
- Create a regular file as the last component of a file target and a
  directory for any other target.
- Refuse repeated children, overlapping targets, and targets that the
  runtime later binds over, such as the machine ID file.
- Mount a single share at its target with its mode and `nosuid,nodev`.
- Mount an aggregate at a root-only location outside the workload root and
  bind each child at its target with its mode and `nosuid,nodev`.

The workload's mount namespace inherits these mounts, and teardown unmounts
the binds in reverse order before the aggregate. Any refusal or mount failure
aborts the sandbox instead of starting the workload without its shares. A
managed sandbox records its shares when it is provisioned and reattaches them
on every start. A [managed layered root](#414-managed-layered-root) may
instead receive host directories as a host mapping table, and a platform
clone must.

## 4.1.3 Blockless Managed Root

Without image layers, each workload runs directly in the guest's initramfs
root, inside a dedicated execution cgroup. Host directories reach it through a
host mapping table rather than an image:

- The host planner refuses a read-only path inside a read-write mapping on
  every host. A read-write path inside a read-only mapping remains valid.
- The host exports the outermost mapped directories, and each mapped file
  outside them on its own, as numbered children of one aggregate, so a file
  child exposes only its file. The guest agents mount the aggregate at a
  root-only location before they accept control traffic.
- The host enforces each mapping's access itself: a child is read-write only
  if it holds a read-write mapping, and writes are limited to read-write
  mappings. A whole volume is never mapped, and a mapping table that would
  need more children than an aggregate holds is refused rather than exported
  through the directories of its files, which would expose more than the
  files.
- The kernel command line announces the number of mappings, and the host
  delivers the table over the
  [control interface](4.4-host-guest-control-interface.md). The guest agents accept
  entries only in order and up to the announced count, validate each request
  before mounting anything, and bind-mount each source at its target with
  `nosuid,nodev`, read-only when requested. They refuse to run workloads until
  every announced mapping is mounted, and a failed mount keeps them refusing.

The blockless root may create the workload account that its adapter requests.

## 4.1.4 Managed Layered Root

In a managed lifecycle, the layered sandbox root uses the shared guest
runtime and host libraries for root assembly, host mappings and execution.
NVX's adapter speaks
[NVXC v2](4.4-host-guest-control-interface.md#444-protocol-versions) over
NVXS; other adapters may carry their own application framing over NVXS and
keep their own admission policy. Unlike the blockless root, it never creates
workload accounts. The identity must already exist in the image, or the
adapter must select numeric IDs without an account check. It differs from a
one-shot layered root in four ways:

- **Readiness.** The guest agents assemble the root from boot tokens without
  waiting for the host, then start the control service. Readiness therefore
  means that the root is assembled and the control path is established, and
  the readiness report names the activation configuration that the guest
  consumed.
- **Host directories.** The command line may announce a number of host
  mappings, which the host delivers over the control interface after
  readiness, as for the [blockless managed root](#413-blockless-managed-root).
  The guest agents mount the aggregate at a root-only location outside the
  workload root and bind each mapping at its target inside the assembled
  root, creating targets under the rules of
  [Live Host Shares](#412-live-host-shares), with `nosuid,nodev`, and
  read-only when requested. An announced count of zero mounts nothing.
- **Executions.** Each execution enters the assembled root with the
  workload's identity and isolation and runs in its own child cgroup of the
  workload cgroup; see
  [Containment](4.2-guest-agents-and-workload-model.md#422-containment).
- **Platform clones.** A clone of a `platform` snapshot receives the same
  activation configuration in the restore packet's activation record instead
  of boot tokens, and its host directories only as a host mapping table,
  because its command line, fixed at capture, carries no share tokens; see
  [Platform-Clone Activation](5.5-restore-protocol.md#559-platform-clone-activation).
