# 4.1 Guest Filesystem and Image Model

[Architecture documentation](README.md) >
[4. Guest Runtime Architecture](4-guest-runtime-architecture.md)

As Table 4.1 shows, the guest runs its workloads in one of two roots, one for
the whole VM.

**Table 4.1.** Workload roots.

| Root | Construction | Host content |
| --- | --- | --- |
| Layered sandbox root | nvx-init's overlay of the read-only layers of one image, an EROFS file system or a GPT disk, under a private writable upper, on scratch or in guest memory | Live host shares that the boot names, or the mappings of a host mapping table |
| Blockless managed root | The guest's own initramfs root, without block devices | Live host shares that the boot binds, or the mappings of a host mapping table |

The guest kernel provides the facilities that the roots need: virtio-blk with
GPT partitions, virtio-fs, EROFS with compression and extended attributes,
ext4, tmpfs with extended attributes, and overlayfs. In neither root does an
execution get a cgroup or a namespace of its own; see
[Isolation and Resource Model](4.3-isolation-and-resource-model.md).

## 4.1.1 Layered Sandbox Root

A layered root's guest runs nvx-init, which builds the root as the VM's one
space. The space is NVX's internal reference code that nvx-init implements,
not public `nvx` API; the guest-agent guidelines'
[Build the space](../guest-agent-guidelines.md#build-the-space) gives its
rules. As Figure 4.1 shows, the root combines the read-only layers of one
immutable `distro` image with one private writable upper: either an ext4
scratch device or a tmpfs in guest memory.

```text
/run/nvx/layers/distro  (EROFS image) -------> lower directory
  or /run/nvx/layers/pN (ext4 layer in partition N of a GPT disk,
                         from partition 2 on) --> lower directories
/run/nvx/scratch/upper  (ext4) --------------> upper directory
  or /run/nvx/tmpfs/upper (tmpfs)
/run/nvx/scratch/work   (same ext4) ---------> work directory
  or /run/nvx/tmpfs/work (same tmpfs)
                  overlay --> /run/nvx/rootfs, moved onto / at the switch
live share: one directory ---> /run/nvx/rootfs/TARGET
  or an aggregate         ---> /run/nvx/shares, each child bound at
                               /run/nvx/rootfs/TARGET
host export: an aggregate ---> /run/nvx/hostfs/root, each mapping of the
                               table mounted at TARGET in the root
```

**Figure 4.1.** Layered sandbox root assembly.

The `distro` image is required and holds a curated base operating system: an
EROFS file system, the overlay's one lower layer, or a GPT disk, whose
partitions after the first each hold an ext4 layer. One immutable image file
can serve many sandboxes, and compressed EROFS reduces stored and cached image
bytes, because the guest kernel decompresses blocks as it reads them. No FUSE
daemon or in-guest fetch service is involved in the root filesystem.

The launcher describes the root to the guest in two boot tokens, and in up to
four more for its settings, whose grammar one contract module defines, with the
host's renderer and a parser for guests:

- `nvx_layer=distro,0xd0003000,FORMAT[:IDENTITY]` names the image on the
  `distro` block device: its format, `erofs` for an EROFS filesystem or `gpt`
  for a GPT disk, and the identity that the guest expects of it, if any, the
  filesystem UUID or the disk GUID in canonical lowercase text. No token names
  a partition GUID.
- `nvx_scratch=0xd0006000,ext4` keeps the overlay's upper on the whole-device
  ext4 `scratch` disk, and `nvx_overlay_upper=ramfs` keeps it in guest
  memory, on a tmpfs, with no `scratch` block device.
- `nvx_overlay_mode=trusted-lowers` or `untrusted-lowers` names the overlay's
  option set, `nvx_scratch_journal=allowed` or `forbidden` whether the
  scratch's ext4 filesystem may have a journal, `nvx_first_partition_bound`
  the most bytes of a GPT disk's first partition, and `nvx_ram_upper_percent`
  the tmpfs upper's cap, from 1 to 90 percent of the guest's memory. A number
  is decimal, without a sign or leading zeros. The guest takes its default for
  a setting without a token: trusted lowers, a journal allowed, and the
  kernel's default size of a tmpfs.

Guests refuse a token without a value, a repeated token, both uppers, an image
without an upper or an upper or a setting without an image, a setting of
another upper or of another format, a RAM upper beside a `scratch` block
device, and every other form, including the earlier `nvx_layer` form without a
format, rather than probe the devices. nvx-init assembles every form that the
tokens name: either image format, over either upper, with either overlay mode,
and it checks a scratch for a journal when the tokens forbid one.

nvx-init builds the root in this order:

1. The early boot, the shell `/init`, mounts the kernel's file systems and a
   tmpfs at `/run`, starts the time daemon, configures the network, and starts
   the announcer when the network publishes the workload's listeners. It then
   replaces itself with nvx-init, which takes the helpers over as PID 1's
   children.
2. nvx-init reads the boot tokens of the root, of the view, and of its own
   settings, such as the workload identity and the control terminal, and
   refuses an incomplete or conflicting set before it mounts anything.
3. It finds each role's block device by its MMIO address, through the
   kernel's platform-device resources rather than a device name or an
   enumeration order, checks that the `distro` device is read-only and the
   scratch writable, and flushes their cached buffers. It checks the image
   before it mounts anything: an EROFS image's filesystem UUID, when the token
   names one, or a GPT disk's partition table, its disk GUID, when the token
   names one, and each layer's ext4 superblock, which must not need a journal
   recovery. When the tokens forbid one, it also checks that the scratch's
   ext4 file system has no journal.
4. It mounts the image's layers read-only, then the upper, on which it creates
   the overlay's upper and work directories: the scratch's ext4 file system
   with `rw,nosuid,nodev`, or a tmpfs with `mode=0755,nosuid,nodev`, and
   `size=N%` when `nvx_ram_upper_percent=N` caps it, or else at the kernel's
   default size, half of the guest's RAM.
5. It mounts the overlay with `nosuid,nodev`, the layers as its lower
   directories, and the option set of its mode: metadata-only copy-up and
   extended inode numbers for trusted lowers, or, for untrusted lowers, a set
   under which the overlay neither creates nor follows metacopy and redirect
   attributes. It then checks that the kernel applied each option, rather than
   accept an overlay that the kernel mounted read-only or without one.
6. It mounts the host export, when the boot names one, out of the root, below
   the runtime directory, where only the guest's root user reaches it.
7. It makes every mount of the root's tree `nosuid` and `nodev`, and mounts
   the root's runtime file systems: `/proc`; a read-only `/sys`; a `/dev` that
   holds only the null, zero, full, random, urandom, and tty devices, with
   `/dev/pts` and `/dev/shm`; and `/run`, with the guest's time status bound
   read-only at `/run/nvx/time`. The boot's live shares follow, as 4.1.2
   describes, since the `/run` tmpfs would hide one beneath `/run`.
8. It opens the descriptors of the root and of its `/run` mount, beneath which
   the mapper binds the host's mappings, resolves the workload's account in
   the root's user and group databases, creating it when the boot asks, opens
   its control terminal, and applies the VM-wide view: it sets the hostname,
   keeps the image's machine ID or binds a generated one over it, and binds a
   resolver file that names the boot's DNS server, if any, over the image's.
9. It switches into the root, once: it moves the root's mount onto `/`, then
   enters it with `chroot` and `chdir`. From then on, nothing unmounts the
   root, and the VM ends by powering off.

Until the switch, a step that fails starts no workload: nvx-init ends the VM,
whatever the root's attempt to unmount what it mounted leaves mounted. After
the switch, nvx-init serves its control session: it applies the host's mapping
table as the host sends it, and runs executions once the table is complete.

A restore of a platform capture builds the same root before Ready, from its
activation record rather than from boot tokens: nvx-init assembles the
record's image over a fresh upper, refusing an `upper` or `work` directory
that holds anything, mounts the host export, if any, applies the record's
view, mounts the runtime file systems, and switches; see
[Complete a restore before Ready](../guest-agent-guidelines.md#complete-a-restore-before-ready).

The UUID check detects attachment mistakes; it is not a content-integrity
proof, and neither the guest nor the VMM verifies layer contents. With
trusted lowers, metadata-only copy-up interprets overlay metadata stored in
the image's layers, so they are trusted inputs that must not carry untrusted
overlay attributes; untrusted lowers copy a file's data up with its metadata
instead. A metadata-only change avoids copying file contents, but a data write
still copies the whole lower file into the upper, so the upper's capacity must
account for copy-up. The two uppers spend different resources:

- Scratch consumes host storage rather than guest RAM, can run out of space
  independently of guest memory pressure, and keeps a managed sandbox's
  changes from one start to the next.
- A RAM upper consumes guest memory, and its cap, the one limit that nvx-init
  sets within the VM, bounds the files that the upper holds, as
  [Priority and Resources](4.3-isolation-and-resource-model.md#433-priority-and-resources)
  describes. The guest has no swap, so those pages stay resident until their
  files are removed. A write beyond the cap fails with `ENOSPC`, and nothing
  that the upper holds outlives the virtual machine.

The initramfs is not a layer of the root: it stays the root of the helpers,
which run from it, while nvx-init leaves it at its switch. A cold boot with a
RAM upper takes the machine's RAM-backed overlay layout, which has exactly one
read-only `distro` block and no scratch; see
[Storage Configuration](2.1-machine-model-and-configuration.md#213-storage-configuration).

## 4.1.2 Live Host Shares

A live share exposes a host directory, such as a source checkout or a tool
cache, or a single host file, such as a settings file, to the workload without
copying it into an image: edits are visible on both sides without staging or
copy-back.

One shared directory can attach to OpenVMM's host filesystem device as a
directory export. Several shares, or any shared file, attach as an aggregate
whose children are independent volumes with their own access modes and
policies; see [Host Filesystem](3.6-host-filesystem.md). NVX's CLI attaches
its shares through one aggregate, the host export, whose children, named by
their index, are the outermost shared directories and the shared files
outside them. Before launch, its `run` and `sandbox` commands refuse guest
targets that overlap one another or that the guest's root reserves.

A boot that names its shares in its tokens, with one share token per bind,
which names its source, a child or, in a blockless root, a path in one, its
guest target, its mode, and whether it is a file, has them in place before any
workload runs:

- In a blockless root, the guest's `/init` mounts the device where the host
  filesystem's tokens name it, with their mode, and binds each token's source
  at its target with its mode, `nosuid`, and `nodev`, creating a missing
  directory, or a regular file for a file, whose target must not be a symbolic
  link.
- In a layered root, nvx-init mounts them once the root's runtime file systems
  are mounted. Before it mounts anything for them, the root checks every
  target: an absolute, canonical path, none that the root's runtime reserves,
  such as `/proc`, `/etc/machine-id`, or `/run/nvx/time`, and none that
  equals, holds, or lies inside another. It mounts the device out of the root,
  below the runtime directory, and its mapper then moves a directory export
  onto its target, or binds each child of an aggregate at its own, beneath the
  overlay's descriptor, through no symbolic link, creating what a target lacks
  only on the root's own mounts, with the share's mode, `nosuid`, and `nodev`
  set before the mount is visible.

Any refusal or mount failure ends the boot instead of starting a workload
without its shares.

A managed sandbox records its shares when it is provisioned, and on every
start receives them as the blockless root receives its host directories (see
4.1.3): the host exports every share as a numbered child of one aggregate,
which nvx-init mounts out of its root, and delivers the mapping table once
nvx-init is ready. nvx-init maps each entry beneath its root, whose own mount
is the overlay, and refuses the targets that the root's runtime reserves, as
it refuses those of a boot's live shares. A mapping that fails ends the start:
the host stops the VM, which nvx-init powers off without unmounting its root.

## 4.1.3 Blockless Managed Root

Without image layers, the managed agent, PID 1, runs each execution as a plain
process directly in the guest's initramfs root, which it never leaves. Host
directories and files reach it as the live shares that its boot binds, or
through a host mapping table, as they reach a managed sandbox, rather than
through an image:

- The host exports the outermost mapped directories, and each mapped file
  outside them on its own, as numbered children of one aggregate, so a file
  child exposes only its file. The guest agents mount the aggregate at a
  root-only location before they accept control traffic.
- The host enforces each mapping's access itself: a child is read-write only
  if it holds a read-write mapping, and writes are limited to read-write
  mappings. A whole volume is never mapped, and a mapping table that would
  need more children than an aggregate holds is refused rather than exported
  through the directories of its files, which would expose more than the
  files.
- The kernel command line announces the number of mappings, or a restored
  nvx-init's activation record does, and the host delivers the table in parts
  over the [control interface](4.4-host-guest-control-interface.md). Each
  guest agent, the managed agent here and nvx-init in a layered root, keeps
  its account of the table in the public `MappingTable`, which accepts parts
  only in order and up to the announced count, refuses a part as a whole
  before anything of it is mounted, and hands each part's mappings, in order,
  to the agent's mapper, part of NVX's internal reference space. The mapper
  walks to each target beneath the descriptor of its root, a mount of a whole
  file system rather than a bind of a directory, through no symbolic or magic
  link, creates what the target lacks only on the root's own mounts, never
  inside another mapping, and attaches a copy of the source's mount there
  with `nosuid,nodev`, read-only when requested, set before the mapping is
  visible. The agents refuse to run workloads until every announced mapping
  is mounted, and a failed mapping latches the table, which keeps them
  refusing.
  [The host's mapping table](../guest-agent-guidelines.md#the-hosts-mapping-table)
  gives the table's contract.
