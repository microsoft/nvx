# 4.4 Host-Guest Control Interface

[Architecture documentation](README.md) >
[4. Guest Runtime Architecture](4-guest-runtime-architecture.md)

Managed operation uses the dedicated control console rather than the boot
console. The VMM owns the outer NVXS v1 transport: bounded framing, same-user
local endpoint authorization, capability authentication, reconnect epochs,
and receive-credit backpressure; see
[Control Console](3.3-consoles.md#332-control-console). The guest agents own
the NVXC v2 application protocol carried inside that stream. Boot diagnostics
and kernel messages stay on the consoles, so framed control traffic never
shares an unstructured byte stream with them.

## 4.4.1 Operations

Table 4.2 lists the operations of the control protocol.

**Table 4.2.** Control operations.

| Operation | Purpose |
| --- | --- |
| `READY` | Reports the application version, guest build ID, and root profile, and is the success reply to requests that return no other data |
| `MAPS` | Delivers a contiguous range of host mapping-table entries |
| `EXEC` | Runs one workload with a timeout, arguments, optional working directory and environment, and standard input |
| `CANCEL` | Kills the running execution that the request names |
| Shutdown | Shuts the VM down gracefully between executions |

An execution request carries a 32-bit timeout and length-prefixed arguments,
and optionally an absolute working directory of at most 4,096 bytes and up to
256 `KEY=VALUE` environment entries of at most 4,096 bytes each, with
distinct, non-empty keys. The environment either replaces the default
environment or is layered over it, each entry replacing the default variable
of the same name. Standard input, standard output, and standard error stream
within per-execution credit windows. Only data in flight is bounded; there is
no total output limit. As Table 4.3 shows, an execution that runs ends with an
exit report, which carries an outcome category, status, and output-truncation
flag.

**Table 4.3.** Exit outcomes.

| Outcome | Meaning |
| --- | --- |
| `exit` | The workload exited; the status is its exit status |
| `signal` | A signal ended the workload; the status is 128 plus the signal number |
| `timeout` | The workload exceeded its timeout and was killed; the status is 124 |
| `cancelled` | A cancellation killed the workload; the status is 137 |
| `failed` | The guest agents could not supervise the workload; the status is 125 |

Otherwise, the guest agents reply with an error, which carries one of the
categories in Table 4.4 and a status. An error refuses a request that the
guest agents cannot carry out, or takes the place of the exit report of an
execution that could not start or whose processes the guest agents could not
account for.

**Table 4.4.** Error categories.

| Category | Meaning |
| --- | --- |
| `launch-failed` | The guest agents could not prepare the execution |
| `cwd-failed` | The workload could not enter its working directory; the status is the error number |
| `containment-failed` | The guest agents could not prove that every workload process exited |
| `mapping-failed` | A host mapping could not be mounted |
| `mappings-incomplete` | Not every announced host mapping is mounted yet |
| `busy` | Another execution is running; NVXC runs one execution at a time |
| `invalid-request` | The request is malformed or invalid in the current configuration |
| `unsupported-operation` | The guest does not implement the operation |

## 4.4.2 Readiness and Bundle Conformance

NVXC has one application version, v2. `READY` carries that version, the guest
build ID, and the root profile. A managed layered root also carries its
activation-configuration identity. The build derives its ID at build time
from its build inputs.

On every fresh session, the host validates `READY` against the selected
bundle before it sends `MAPS` or `EXEC`. It terminates a guest whose
application version, build ID, root profile, or required activation identity
does not match. A restored guest reports the build captured in its snapshot,
so the host compares it with the bundle that built the template.

## 4.4.3 Session Semantics

Requests are typed, length-bounded, ordered, and associated with one VM
instance and epoch. Credit limits bound queued data in both directions.
Malformed, unauthenticated, stale, duplicated, or out-of-order records fail
closed. NVXC runs one execution at a time: any request other than a
cancellation that arrives during an execution is refused as `busy`; standard
input and credit records belong to the running execution and are not
requests. Shutdown is therefore graceful only between executions: a host
cancels a running execution before it requests shutdown. Other adapters carry
their own framing over NVXS and set their own concurrency.

Normal completion is lossless: the exit report follows the last output of
both streams. On cancellation, timeout, handle drop, disconnect, reset, or
Stop, pending output drains for a bounded grace period. The guest then
discards any remainder and sets the output-truncation flag, so teardown cannot
wait indefinitely for a reader. Control and timers stay live throughout. The
logical outcome, delivery completion and process settlement are separate: an
execution completes only after its descendants settle.

The control session is process-local even when guest parser state is
snapshotted. Restore establishes a fresh host capability, peer identity,
instance, and epoch, and the guest agents acknowledge the new instance before
any host data reaches them. A request from before the capture therefore can
never be replayed into a clone or a resumed process.

Secrets and per-execution environments belong on the authenticated control
channel, not in the kernel command line, image layers, scratch, snapshot
metadata, or the restore packet's activation record. Boot configuration that
the machine profile owns contains only the non-secret invariants needed before
the control channel exists.

## 4.4.4 Protocol Versions

NVXC v2 uses piped standard input with an explicit end of input and gives each
execution its own credit windows in both directions. The host grants credit
for standard output and standard error as it consumes them, and the guest
grants credit for standard input as the workload drains it. A guest without
credit stops reading the workload's output, which blocks the workload instead
of killing it. Cancellation, credit grants, and session control still
progress while an execution's window is exhausted.

NVXC execution credits are separate from the outer NVXS v1 transport's byte
credits. NVXC provides no terminal, window resizing, or signals other than
cancellation.
