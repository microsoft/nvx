# 4.4 Host-Guest Control Interface

[Architecture documentation](README.md) >
[4. Guest Runtime Architecture](4-guest-runtime-architecture.md)

Managed operation uses the dedicated control console rather than the boot
console. The VMM owns the outer transport: bounded framing, same-user local
endpoint authorization, capability authentication, reconnect epochs, and
receive-credit backpressure; see
[Control Console](3.3-consoles.md#332-control-console). The guest agents own
the workload protocol carried inside that stream. Boot diagnostics and kernel
messages stay on the consoles, so framed control traffic never shares an
unstructured byte stream with them.

## 4.4.1 Operations

Table 4.2 lists the operations of the control protocol.

**Table 4.2.** Control operations.

| Operation | Purpose |
| --- | --- |
| `READY` | Reports readiness, and is the success reply to requests that return no other data |
| `FEATURES` | Reports which control behaviors the guest image provides |
| `MAPS` | Delivers a contiguous range of host mapping-table entries |
| `EXEC` | Runs one workload with a timeout, arguments, and an optional working directory and environment, and, in protocol version 2, standard input |
| `CANCEL` | Kills the running execution that the request names |
| Shutdown | Shuts the VM down gracefully between executions |

An execution request carries a 32-bit timeout and length-prefixed arguments,
and optionally an absolute working directory of at most 4,096 bytes and up to
256 `KEY=VALUE` environment entries of at most 4,096 bytes each, with
distinct, non-empty keys. The environment either replaces the default
environment or is layered over it, each entry replacing the default variable
of the same name. Output returns as separate standard output and standard
error streams within the credit window. Protocol version 1 allows at most
1 MiB of them combined for each execution; version 2 streams them without a
total limit, as [Protocol Versions](#444-protocol-versions) describes. As
Table 4.3 shows, an execution that runs ends with an exit report, which
carries an outcome category and a status.

**Table 4.3.** Exit outcomes.

| Outcome | Meaning |
| --- | --- |
| `exit` | The workload exited; the status is its exit status |
| `signal` | A signal ended the workload; the status is 128 plus the signal number |
| `timeout` | The workload exceeded its timeout and was killed; the status is 124 |
| `cancelled` | A cancellation killed the workload; the status is 137 |
| `output-limit` | In protocol version 1 only, the workload's combined output exceeded 1 MiB, and the guest agents killed it; the status is 125 |
| `failed` | The guest agents could not supervise the workload; the status is 125 |

Otherwise, the guest agents reply with an error, which carries one of the
categories in Table 4.4 and a status. An error refuses a request that the
guest agents cannot carry out, or takes the place of the exit report of an
execution that could not start or whose processes the guest agents could not
account for.

**Table 4.4.** Error categories.

| Category | Meaning |
| --- | --- |
| `launch-failed` | The guest agents could not prepare the execution |
| `cwd-failed` | The workload could not enter its working directory; the status is the error number |
| `containment-failed` | The guest agents could not prove that every workload process exited |
| `mapping-failed` | A host mapping could not be mounted |
| `mappings-incomplete` | Not every announced host mapping is mounted yet |
| `busy` | Another execution is running |
| `invalid-request` | The request is malformed or invalid in the current configuration |
| `unsupported-operation` | The guest does not implement the operation |

## 4.4.2 Feature Negotiation

A successful readiness probe does not prove that an image enforces the
behaviors that a host depends on. As Table 4.5 shows, a `FEATURES` request
therefore returns a four-byte little-endian bit mask of control features.

**Table 4.5.** Control feature bits.

| Bit | Feature |
| ---: | --- |
| 0 | Cancellation |
| 1 | Reserved; never set |
| 2 | Workload account creation |
| 3 | Per-execution cgroup containment |
| 4 | Per-execution environment |
| 5 | Working-directory refusal |
| 6 | Host mapping table |

The blockless managed root and the
[managed layered root](4.1-guest-filesystem-and-image-model.md#414-managed-layered-root)
provide all six features. A feature bit is added together with the behavior
it names. Hosts ignore unknown bits and trailing bytes, read an
`unsupported-operation` refusal as no features, and terminate a guest that
lacks a feature they need instead of running workloads without the policy
they requested.

A host and guest built together as a matched bundle need no `FEATURES`
request when they speak protocol version 2, because the bundle fixes the
features and the guest's readiness report carries its protocol version and
build identity. The host terminates a guest whose identity differs from the
bundle's instead of probing it per operation. A restored guest reports the
build captured in its snapshot, so the host compares it with the bundle that
built the template.

## 4.4.3 Session Semantics

Requests are typed, length-bounded, ordered, and associated with one VM
instance and epoch. Credit limits bound queued data in both directions.
Malformed, unauthenticated, stale, duplicated, or out-of-order records fail
closed. Only one execution runs at a time; any request other than a
cancellation that arrives during an execution is refused as `busy`. The
standard input and credit records of a version-2 execution belong to the
running execution and are not requests. Shutdown is therefore graceful only
between executions: a host cancels a running execution before it requests
shutdown, or else terminates the VM, which fails the execution.

The control session is process-local even when guest parser state is
snapshotted. Restore establishes a fresh host capability, peer identity,
instance, and epoch, and the guest agents acknowledge the new instance before
any host data reaches them. A request from before the capture therefore can
never be replayed into a clone or a resumed process.

Secrets and per-execution environments belong on the authenticated control
channel, not in the kernel command line, image layers, scratch, snapshot
metadata, or the restore packet's activation record. Boot configuration that
the machine profile owns contains only the non-secret invariants needed before
the control channel exists.

## 4.4.4 Protocol Versions

The control protocol has two versions, which differ in their readiness report
and their execution streams. A session uses one version throughout. A
version-2 guest states its protocol version and build identity in its
readiness report and, in a managed layered root, the identity of its
activation configuration; a readiness report without them comes from a
version-1 guest. A host that requires another version terminates the guest
instead of downgrading a requested stream.

- **Version 1** is the protocol that the preceding sections describe. An
  execution has no standard input, its output flows within the session's
  credit window, and its combined output is limited to 1 MiB.
- **Version 2** adds piped standard input with an explicit end of input, and
  gives each execution its own credit windows in both directions. The host
  grants credit for standard output and standard error as it consumes them,
  and the guest grants credit for standard input as the workload drains it.
  Output therefore has no total limit; only data in flight is bounded, and a
  guest without credit stops reading the workload's output, which blocks the
  workload instead of killing it. Execution credits are separate from the
  control console's receive credit. The exit report follows the last output
  of both streams, so a host that withholds credit delays it, but a
  cancellation, credit grants, and session control still progress while an
  execution's window is exhausted.

Both versions run one execution at a time and keep every other operation,
outcome, and error. Neither provides a terminal, window resizing, signals
other than cancellation, or concurrent executions; these remain outside the
control protocol.
