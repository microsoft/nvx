# 5.2 Readiness and Runtime Control

[Architecture documentation](README.md) >
[5. VM Lifecycle and State](5-vm-lifecycle-and-state.md)

Readiness is an explicit lifecycle boundary, not the observation of arbitrary
console text. A cold boot is usable when the guest agents have initialized the
required devices and either prepared the one-shot workload or established the
managed control path. In a
[managed layered root](4.1-guest-filesystem-and-image-model.md#414-managed-layered-root),
the guest agents assemble the workload root before they establish the control
path, so readiness also means that the root is assembled; a platform clone
reaches the same state through
[activation](5.5-restore-protocol.md#559-platform-clone-activation).

## 5.2.1 Control Frontends

Two frontends drive the VM worker: command-line launch and the management
RPC. Both construct the same machine profile, and the worker applies the same
validation, snapshot boundaries, and management exclusion to both. The
management RPC creates, captures, and restores machines without sandbox
blocks, a network device, or a control console, attaches the byte channel,
the boot console, and one host filesystem export, publishes readiness, and
reports guest exit. Generic host-initiated save and pulse save-and-restore
operations are unavailable for the microVM: capture is always
guest-requested.

## 5.2.2 Readiness Endpoint

An orchestrator may supply a single-use readiness endpoint for a restore: an
existing Unix socket on Linux or named pipe on Windows. The VMM connects to it
before the worker launches. When the restored VM first starts, the worker
writes one fixed readiness record after every state unit has started and
before it releases a restored processor. For a gated restore, host input is
still gated at that point, and guest repair and its acknowledgement follow
the event. A connection, write, or flush failure aborts startup, and the
endpoint is never saved in a snapshot. The event marks a started VM, not a
usable one: in a platform clone, activation also follows it, so a host runs
workloads only after the guest agents report readiness over the control
channel.

## 5.2.3 Management Exclusion

While the worker holds the snapshot stop guard, its central dispatcher
immediately rejects management operations that could disturb the boundary,
including memory writes, resume or reset, device changes, and state dumps,
rather than queueing them. Snapshot quiesce, rollback, boundary release, and
memory reads remain available. The exclusion applies at the worker boundary
that every management frontend shares.

## 5.2.4 Managed Sandbox Lifecycle

As Table 5.2 shows, host launchers present a persistent sandbox with five
operations.

**Table 5.2.** Managed sandbox operations.

| Operation | Effect |
| --- | --- |
| Provision | Records the sandbox's configuration, including its host shares |
| Start | Launches the VMM with a freshly generated control capability, reattaches the recorded shares, waits for guest readiness, and delivers any host mapping table, completing once every announced mapping is mounted |
| Exec | Runs one workload over the control channel |
| Stop | Shuts down the VM and releases its runtime resources |
| Deprovision | Removes the sandbox's state |

Lifecycle transitions fail closed and take effect one at a time per sandbox,
while executions run beside them. The host identifies the running VMM process
of each sandbox, reconciles VMM processes with recorded state, and recovers
interrupted launches. Teardown leaves no VMM process, control endpoint,
capability, or runtime record, while supplied layers and scratch survive.

The host runs one execution at a time per sandbox, as the guest does, and
holds requests that arrive meanwhile in a bounded queue rather than forwarding
them for the guest to refuse as `busy`. A full queue refuses a request at
once, and a waiter whose deadline passes or whose caller leaves never starts.
Stop takes priority over the queue: it fails the waiters, cancels the running
execution, and shuts the VM down, or terminates the VM when the execution
cannot be cancelled within a bound.

The sandbox lifecycle API exposes the same operations with request
validation, backend capabilities, durable records, and stable error codes. Its
default backend launches the VMM directly with the managed lifecycle and the
blockless managed root. Its image-backed backend runs the
[managed layered root](4.1-guest-filesystem-and-image-model.md#414-managed-layered-root)
through the host control library and the guest runtime library, which an
embedding host may also drive through its own adapter, for example in a
separately supplied native library.

## 5.2.5 Authority

Runtime control is divided by authority:

- The host controller may request supported VM lifecycle transitions.
- The VMM serializes transitions that affect machine state.
- The guest agents own workload start, stop, supervision, and capture
  preparation.
- The workload cannot invoke host management interfaces directly.

Operations that could disturb a capture or restore boundary are rejected
while that boundary is active rather than queued for later execution.
