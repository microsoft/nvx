# 5.1 Boot Protocol

[Architecture documentation](README.md) >
[5. VM Lifecycle and State](5-vm-lifecycle-and-state.md)

Cold boot consumes a host-selected kernel, optional initramfs, initial RAM
size, processor capacity, device attachments, and workload policy. The
machine profile validates these inputs and constructs the complete effective
configuration before opening guest execution.

## 5.1.1 Linux Direct Loader

The loader treats the kernel, initramfs, command line, topology,
reservations, and guest addresses as untrusted. It:

1. Requires a little-endian, uncompressed ELF64 image for x86-64 and rejects
   the compressed, self-extracting Linux kernel format (bzImage).
2. Loads validated loadable segments at their physical addresses and zeroes
   their BSS tails.
3. Places an optional initramfs at the first 2-MiB boundary after the kernel.
4. Builds the Intel MP 1.4 processor, ISA bus, IOAPIC, and legacy interrupt
   entries.
5. Builds Linux `boot_params` with the canonical e820 RAM and reservation map.
6. Installs a bootstrap GDT and 4-GiB identity page tables.
7. Enters the kernel in the 64-bit execution mode of x86-64 (long mode) with
   paging enabled.

No firmware executes, and the loader neither parses nor produces the boot
metadata of Xen's direct-boot entry point (Xen notes or start-info
structures), ACPI tables, the pointer through which an operating system
locates them (RSDP), SMBIOS data, or a device tree. The zero page leaves the
ACPI RSDP address zero.

Table 5.1 lists the initial processor state.

**Table 5.1.** Initial processor state.

| Register | Value |
| --- | --- |
| Instruction pointer (`RIP`) | ELF entry point |
| General-purpose register that carries the boot-parameter pointer (`RSI`) | `0x2000`, the `boot_params` zero page |
| Page-table base (`CR3`) | `0x4000`, the identity page tables |
| Processor control (`CR0`) | Protected mode (`PE`) and paging (`PG`) set |
| Extended processor control (`CR4`) | Physical address extension (`PAE`) set |
| Extended feature enable (`EFER`) | Long mode enabled |

## 5.1.2 Effective Command Line

The machine profile, not the caller, owns console, device-discovery, and
host-policy tokens. The base command line is:

```text
earlycon=xe9 console=hvc0 reboot=t panic=-1
```

When the boot virtio-console is present, the kernel console becomes `hvc1`,
and the byte channel remains the early console. User arguments follow the
base tokens. A fresh boot then appends host-owned tokens in this order:

1. `nr_cpus=<capacity>`, so Linux sizes its processor state to the validated
   topology.
2. The optional fixed workload identity, `nvx_workload_uid=` and
   `nvx_workload_gid=`, and the workload lifecycle, `nvx_lifecycle=`.
3. `nvx_snapshot_tier=<tier>` for a capture with sandbox blocks.
4. Device-discovery tokens in fixed address order: network, host filesystem,
   boot console, sandbox blocks, and the control console followed by
   `nvx_control_tty=hvc2`.
5. Network bootstrap tokens, including a DNS server only when the egress
   policy permits DNS to a gateway and, last, the ingress mode when the host
   publishes the guest's listeners, followed by the host filesystem bootstrap
   tokens.

Callers may not supply `earlycon=`, `console=`, `virtio_mmio.device=`,
`nr_cpus=`, any network or host filesystem bootstrap token,
`nvx_snapshot_tier=`, `nvx_workload_uid=`, `nvx_workload_gid=`, or
`nvx_lifecycle=`. A machine with a control console also applies the
[control-console rules](3.3-consoles.md#332-control-console). The command
line carries no clock parameter: the guest reads its TSC and LAPIC rates from
the [time ABI](3.2-clock-and-time.md#324-rates) MSRs, and `tsc_early_khz=` or
`lapic_timer_hz=`, from the caller or a snapshot, is rejected.

Launchers add runtime tokens of their own: the
[boot tokens of a layered root](4.1-guest-filesystem-and-image-model.md#411-layered-sandbox-root),
one share token per host-share child, the number of host mappings for a
blockless managed root, and a request to create the workload account. A caller
may also declare the RAM-backed overlay layout, whose overlay upper the guest
agents keep on a tmpfs, with exactly one `nvx_overlay_upper=ramfs` token; any
other form of that token is rejected.

Embedded NULs are rejected, and the complete NUL-terminated command line must
fit in the x86 guest kernel's `COMMAND_LINE_SIZE` of 2,048 bytes, which leaves
at most 2,047 bytes of text. The kernel silently drops text beyond its limit,
and the host-owned tokens, which come last, would be lost first. An
uncompressed ELF image does not declare that limit to the loader, so the
machine profile applies it as a fixed part of the boot contract: it checks the
effective command line, its own tokens included, and rejects one that does not
fit before any processor runs, instead of truncating it. The effective string
and its SHA-256 digest become part of the snapshot machine contract. A restore
reuses that string verbatim and appends no tokens, so it rejects a saved
command line over the limit instead of rewriting it.

## 5.1.3 Cold Boot Sequence

A cold boot:

1. Selects the CPU profile and rejects clock tokens in the command line.
2. Creates the partition and preflights the backend before any processor
   runs: CPU-profile support, the effective CPUID, identity routing, the
   synchronized-set primitive, and the absence of TSC scaling.
3. Reads and checks the native TSC and LAPIC rates, and declares them as `F`
   and `L`.
4. Loads the guest and sets the generation counter to zero.
5. Starts the state units and releases the processors.

A cold boot writes no TSC: every backend starts the processors' TSCs
together. The kernel then discovers the fixed virtio-mmio devices and starts
the guest agents, which step the guest clock to host UTC before readiness,
assemble the workload root, apply isolation, and start either the one-shot
workload or the managed control service.
