# 1.5 Compatibility and Versioning Model

[Architecture documentation](README.md) >
[1. Architecture Overview](1-architecture-overview.md)

Table 1.1 lists the explicit contracts that define NVX compatibility, and the
owner of each: OpenVMM, or the `nvx` library, which the host's callers and the
guest's inits share. Each contract carries its own version or identity,
independent of the others. A caller's own records, such as the store of NVX's
command-line interface (CLI), and any protocol of its own with its guest are
the caller's to version.

**Table 1.1.** Compatibility contracts.

| Contract | Owner | Governs |
| --- | --- | --- |
| Machine ABI | OpenVMM | CPU topology, memory layout, device topology, addresses, interrupts, transport, and guest-visible policy. |
| Boot layout | OpenVMM | Placement and format of the Linux-direct boot structures: MP tables, bootstrap GDT and page tables, Linux boot-parameter block (zero page), and kernel command line. |
| CPU profile | OpenVMM | Guest-visible CPU surface of one vendor and CPU generation, identified by vendor, generation, and revision, and by the digest of its canonical encoding. |
| Time ABI | OpenVMM | Hypervisor identity, frequency interfaces, clocksources, timers, downtime semantics, and restore-time repair. The guest reads its version from the CPUID functions reserved for hypervisor information (hypervisor identity leaves). |
| Device-private schemas | OpenVMM | Saved queue and device state that must be understood before a device can resume. |
| Snapshot format | OpenVMM | Persisted machine contract, manifest, state inventory, memory geometry, attachment requirements, and artifact identity. |
| RAM expansion capability | OpenVMM | Recorded RAM capacity, memory-block size, and expansion ranges that restore may activate. |
| Restore packet | OpenVMM | Layout and meaning of the one-time record that gives a restored guest its generation, downtime, rate deviation, activation targets, fresh entropy, the network settings of a policy that the restore installs on a snapshot without a tier, and a platform clone's activation record. |
| Control session | OpenVMM | The authenticated session between the host and the guest that the control-console broker frames: its records, credits, authentication, and lifecycle epochs. |
| Management RPC machine profile | OpenVMM | Identity of the microVM machine profile in the management RPC. |
| Boot contract | `nvx` | The microVM ABI on which NVX's guests boot, the kernel command-line tokens through which the host configures them, such as a layered root's image, upper, and view, and the root that the guest assembles from them. |
| Activation record | `nvx` | The settings that a restored layered root applies in place of its captured configuration, and what Ready reports about the activation. |
| Snapshot key | `nvx` | What a VM restored from a strict snapshot directory must match, in one canonical encoding whose digest is the snapshot's compatibility identity. |
| Control protocol | `nvx` | NVX's own requests and responses between its CLI and its guest agents, which the control session carries; private to `nvx`. |

A change to a guest-visible address, interrupt, command-line token, feature
mask, queue shape, time rule, or device behavior requires a new contract
version. A backend-specific difference is valid only when the versioned
contract states it explicitly. A change that only widens a bound that restore
checks keeps the version: every restore that the narrower bound admitted
behaves as before, and a party that predates the change still refuses what
lies beyond its own bound. The contract then states which snapshots the wider
bound serves, and how the others fail, as
[Downtime and Continuity](3.2-clock-and-time.md#328-downtime-and-continuity)
does for the downtime bound.

Guest-visible configuration is immutable for the lifetime represented by a
snapshot. Restore derives the machine from the snapshot manifest; caller input
may reconstruct permitted external resources but cannot silently change the
captured CPU surface, memory capacity, command line, device placement, feature
masks, or network identity.

Compatibility is exact rather than best effort. Unknown versions, missing or
extra devices, changed queue shapes, incompatible CPU surfaces, malformed
state, or mismatched attachments are rejected before guest execution. A
snapshot with an unsupported manifest version must be recaptured.

## 1.5.1 Restore Compatibility

A snapshot restores only:

- On the backend that captured it.
- On a host whose CPU belongs to the generation of the snapshot's CPU profile.
- On a host whose native TSC rate lies within 250 ppm of the snapshot's
  [declared rate](3.2-clock-and-time.md#324-rates).
- With a VMM build that pins the same CPU-profile revision. No build pins a
  [host CPU profile](2.2-cpu-and-topology.md#2212-cpu-profile-selection), so
  its snapshot instead carries the only copy, which must be a valid canonical
  document with the recorded digest.
- With a VMM build that computes the same effective CPUID for that CPU profile
  and topology.
- With external resources that reproduce the recorded attachment identities.
- Within the [downtime bound](3.2-clock-and-time.md#328-downtime-and-continuity)
  of 365 days after its capture, when the snapshot's guest and the restoring
  VMM both have that bound, and otherwise within 30 days.
- Through `nvx`, under the runtime identity that the snapshot's key records;
  see [Runtime Identity](#154-runtime-identity).

Released CPU-profile revisions are immutable and never deleted, so existing
snapshots stay restorable; a normative change creates a new revision.

## 1.5.2 Snapshot Compatibility

A snapshot of `nvx` represents a compatibility class, not an arbitrary fleet
image. When `nvx` finishes a capture, it derives the class from the capture's
context and OpenVMM's manifest alone, without reading a binary, an image, or
the memory, and records it in the snapshot's key: the runtime identity; the
versions of the snapshot format, saved device state, time ABI, restore packet,
and activation record; the backend, the CPU profile, the effective CPUID, the
topology, and the declared rates; the processors and RAM at boot, their
capacities, and the expansion ranges; the effective command line; the
geometries of the placeholder image and the dormant scratch; the devices; the
NIC, if any; and the caller's invariants, up to 64 named settings that `nvx`
keeps without interpreting them. The key's identity, a `KeyIdentity`, digests
all of these, but not the capture's own time fields: its anchors, host clock,
host and boot identities, lineage, and cut-to-anchor interval. Captures of one
class at different times therefore share it, while the declared rates remain
part of it. Restoring guest memory restores the captured guest build, not a
newly deployed initramfs, so a deployment that changes a runtime label
captures its snapshots again.

Processor capacity and RAM geometry are immutable, but restore-time activation
lets one snapshot serve several online processor counts and RAM sizes, from
those at boot to the capacities. Layer-role presence and device geometry stay
fixed: a restore attaches an image with the placeholder's logical and physical
block sizes and at most its length, and a scratch with the dormant scratch's
exact geometry, or, for an upper in RAM, declares the scratch absent. Nothing
of a restore is part of the key: its image, upper, export, view, network
policy, workload, or activation targets.

The key also records the snapshot's NIC, if it has one: the guest's address
and the identity of the complete deny-all policy under which the capture
attached it. Every restore of the snapshot replaces that policy with its own,
so a snapshot serves the restores of every network policy at its guest's
address, and its key records none of them. The key's encoding, version 1, has
not been released, so no key that an earlier build encoded is supported. There
is no migration.

Before it restores a snapshot, `nvx` checks the requested VM against the
snapshot's key and manifest with `Snapshot::accepts`: a layered root;
processor and memory targets within the snapshot's limits; the image and
scratch geometries; the NIC's presence and address; the boot console's captured
attachment; the backend, CPU profile, and runtime identity; and the time
contract's restore window at the host's current time.

## 1.5.3 Persisted State

The snapshot manifest is authoritative for a restored process. Native file
descriptors, sockets, named-pipe handles, and hypervisor objects are never part
of the portable state. They are recreated from stable identities and declared
reconstruction policies.

`nvx` persists no state of its own. Besides the files of a launch in its
caller's VM directory, it writes only a finished capture's key and
description. A caller that must find a running VM again after a restart saves
its own values: the VM's directory, its control endpoint, its capability, its
process reference, and its runtime identity. NVX's CLI keeps them in its own
store, beside records of its own, in formats of its own.

## 1.5.4 Runtime Identity

A VM's runtime identity names the runtime that launched it: a label for each of
its three runtime files, OpenVMM, the guest kernel, and the guest initramfs,
and the versions of the boot contract, the control contract, and the control
session that `nvx` speaks. A label is an opaque token that the caller takes
from the files' install or staging metadata, such as `sha256:` and the digest
that a release's `SHA256SUMS` lists for the file: `nvx` compares labels and
never reads or digests a runtime file, which would cost time in proportion to
its size at every launch. NVX's CLI takes them from a release's `SHA256SUMS`,
or from the build provenance that a repository checkout keeps beside its
artifacts.

The runtime identity decides whether a host keeps driving a VM that it finds
recorded, as after the caller restarts or upgrades its own code. Under the same
identity, `vm::verify` returns the VM's held process, and `vm::reattach`
authenticates again with the saved capability. Under another, `nvx` refuses to
drive the VM through artifacts or contracts that did not start it, with an
error of kind `RuntimeMismatch` that names the parts that differ, and only a
stop through the VM's verified process applies. A snapshot's key records the
runtime identity of its capture, so a snapshot restores only under that
identity.
