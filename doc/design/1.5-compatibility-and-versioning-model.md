# 1.5 Compatibility and Versioning Model

[Architecture documentation](README.md) >
[1. Architecture Overview](1-architecture-overview.md)

Table 1.1 lists the explicit contracts that define NVX compatibility, and the
owner of each: OpenVMM; the `nvx` library, which the host's callers and the
guest's inits share; or NVX's command-line interface (CLI) and the guests that
it bundles. Each contract carries its own version or identity, independent of
the others. A caller's own records, such as the CLI's store, and any protocol
of its own with its guest are the caller's to version.

**Table 1.1.** Compatibility contracts.

| Contract | Owner | Governs |
| --- | --- | --- |
| Machine ABI | OpenVMM | CPU topology, memory layout, device topology, addresses, interrupts, transport, and guest-visible policy. |
| Boot layout | OpenVMM | Placement and format of the Linux-direct boot structures: MP tables, bootstrap GDT and page tables, Linux boot-parameter block (zero page), and kernel command line. |
| CPU profile | OpenVMM | Guest-visible CPU surface of one vendor and CPU generation, identified by vendor, generation, and revision, and by the digest of its canonical encoding. |
| Time ABI | OpenVMM | Hypervisor identity, frequency interfaces, clocksources, timers, downtime semantics, and restore-time repair. The guest reads its version from the CPUID functions reserved for hypervisor information (hypervisor identity leaves). |
| Device-private schemas | OpenVMM | Saved queue and device state that must be understood before a device can resume. |
| Snapshot format | OpenVMM | Persisted machine contract, manifest, state inventory, memory geometry, attachment requirements, and artifact identity. |
| RAM expansion capability | OpenVMM | Recorded RAM capacity, memory-block size, and expansion ranges that restore may activate. |
| Restore packet | OpenVMM | Layout and meaning of the one-time record that gives a restored guest its generation, downtime, rate deviation, activation targets, fresh entropy, the network settings of a policy that the restore installs on a snapshot without a tier, and a platform clone's activation record. |
| Control session | OpenVMM | The authenticated session between the host and the guest that the control-console broker frames: its records, credits, authentication, and lifecycle epochs. |
| Management RPC machine profile | OpenVMM | Identity of the microVM machine profile in the management RPC. |
| Boot contract | NVX's CLI | The microVM ABI on which NVX's bundled guests boot, the kernel command-line tokens through which the CLI configures them, such as a layered root's image, upper, and view, and the root that the bundled init assembles from them. |
| Activation record | `nvx` | The settings that a restored layered root applies in place of its captured configuration, and what Ready reports about the activation. |
| Snapshot key | `nvx` | What a VM restored from a strict snapshot directory must match, in one canonical encoding whose digest is the snapshot's compatibility identity. |
| Control protocol | NVX's CLI | NVX's own requests and responses between its CLI and its guest agents, which the control session carries; private to `nvx`. |

`nvx` interprets only what it reads or writes itself, and keeps each version
private to the code that does: its snapshot-manifest decoder reads version 2
of OpenVMM's snapshot format, version 1 of its microVM ABI, and version 1 of
its time ABI, and refuses a manifest that it cannot interpret; it encodes and
decodes the activation record and the snapshot key; and its optional guest
time helper decodes version 1 of the time ABI and of the restore packet. It
never interprets the schema of OpenVMM's saved device state, which OpenVMM
checks when it restores: a snapshot's key records it, so a snapshot restores
only with the schema that captured it. Whether a runtime's guests speak a boot
contract or a control protocol, and which, is its caller's policy, which the
caller names in the runtime identity; see
[Runtime Identity](#155-runtime-identity).

A change to a guest-visible address, interrupt, command-line token, feature
mask, queue shape, time rule, or device behavior requires a new contract
version. A backend-specific difference is valid only when the versioned
contract states it explicitly. A change that only widens a bound that restore
checks keeps the version: every restore that the narrower bound admitted
behaves as before, and a party that predates the change still refuses what
lies beyond its own bound. The contract then states which snapshots the wider
bound serves, and how the others fail, as
[Downtime and Continuity](3.2-clock-and-time.md#328-downtime-and-continuity)
does for the downtime bound.

Guest-visible configuration is immutable for the lifetime represented by a
snapshot. Restore derives the machine from the snapshot manifest; caller input
may reconstruct permitted external resources but cannot silently change the
captured CPU surface, memory capacity, command line, device placement, feature
masks, or network identity.

Compatibility is exact rather than best effort. Unknown versions, missing or
extra devices, changed queue shapes, incompatible CPU surfaces, malformed
state, or mismatched attachments are rejected before guest execution. A
snapshot with an unsupported manifest version must be recaptured.

## 1.5.1 Restore Compatibility

A snapshot restores only:

- On the backend that captured it.
- On a host whose CPU belongs to the generation of the snapshot's CPU profile.
- On a host whose native TSC rate lies within 250 ppm of the snapshot's
  [declared rate](3.2-clock-and-time.md#324-rates).
- With a VMM build that pins the same CPU-profile revision. No build pins a
  [host CPU profile](2.2-cpu-and-topology.md#2212-cpu-profile-selection), so
  its snapshot instead carries the only copy, which must be a valid canonical
  document with the recorded digest that the build's derivation policy would
  not change.
- With a VMM build that computes the same effective CPUID for that CPU profile
  and topology.
- With external resources that reproduce the recorded attachment identities.
- On a host whose backend can access every
  [processor state element](#154-processor-state-elements) that the snapshot
  holds.
- Within the [downtime bound](3.2-clock-and-time.md#328-downtime-and-continuity)
  of 365 days after its capture, when the snapshot's guest and the restoring
  VMM both have that bound, and otherwise within 30 days.
- Through `nvx`, under the runtime identity that the snapshot's key records;
  see [Runtime Identity](#155-runtime-identity).

Released CPU-profile revisions are immutable and never deleted, so existing
snapshots stay restorable; a normative change creates a new revision.

## 1.5.2 Snapshot Compatibility

A snapshot of `nvx` represents a compatibility class, not an arbitrary fleet
image. When `nvx` finishes a capture, it derives the class from the capture's
context and OpenVMM's manifest alone, without reading a binary, an image, or
the memory, and records it in the snapshot's key: the runtime identity; the
versions of the snapshot format, of the schema of the saved device state, of
the time ABI, and of the activation record; the backend, the CPU profile, the
effective CPUID, the topology, and the declared rates; the processors and RAM
at boot, their capacities, and the expansion ranges; the effective command
line; the geometries of the placeholder image and the dormant scratch; the
devices; the NIC, if any; and the caller's invariants, up to 64 named settings
that `nvx` keeps without interpreting them. The key's identity, a
`KeyIdentity`, digests all of these, but not the capture's own time fields:
its anchors, host clock, host and boot identities, lineage, and cut-to-anchor
interval. Captures of one class at different times therefore share it, while
the declared rates remain part of it. Restoring guest memory restores the
captured guest build, not a newly deployed initramfs, so a deployment that
changes a runtime label captures its snapshots again.

Processor capacity and RAM geometry are immutable, but restore-time activation
lets one snapshot serve several online processor counts and RAM sizes, from
those at boot to the capacities. Layer-role presence and device geometry stay
fixed: a restore attaches an image with the placeholder's logical and physical
block sizes and at most its length, and a scratch with the dormant scratch's
exact geometry, or, for an upper in RAM, declares the scratch absent. Nothing
of a restore is part of the key: its image, upper, export, view, network
policy, workload, or activation targets.

The key also records the snapshot's NIC, if it has one: the guest's address
and the identity of the complete deny-all policy under which the capture
attached it. Every restore of the snapshot replaces that policy with its own,
so a snapshot serves the restores of every network policy at its guest's
address, and its key records none of them. The key's encoding, version 1, has
not been released, so no key that an earlier build encoded is supported. There
is no migration.

Before it restores a snapshot, `nvx` checks the requested VM against the
snapshot's key and manifest with `Snapshot::accepts`: a layered root;
processor and memory targets within the snapshot's limits; the image and
scratch geometries; the NIC's presence and address; the boot console's captured
attachment; the backend, CPU profile, and runtime identity; and the time
contract's restore window at the host's current time.

## 1.5.3 Persisted State

The snapshot manifest is authoritative for a restored process. Native file
descriptors, sockets, named-pipe handles, and hypervisor objects are never part
of the portable state. They are recreated from stable identities and declared
reconstruction policies.

`nvx` persists no state of its own. Besides the files of a launch in its
caller's VM directory, it writes only a finished capture's key and
description. A caller that must find a running VM again after a restart saves
its own values: the VM's directory, its control endpoint, its capability, its
process reference, and its runtime identity. NVX's CLI keeps them in its own
store, beside records of its own, in formats of its own.

## 1.5.4 Processor State Elements

A snapshot holds each piece of a virtual processor's state as an element of its
own, and an element is optional, so a VMM can add one without a new version. A
snapshot captured before the VMM held an element lacks it, and restoring it
leaves that state at its reset value, as the earlier VMM did. A VMM that
predates an element restores a later snapshot without it, ignoring it, so it
loses that state the same way. Neither restore fails, and none of the contracts
of Table 1.1 records which elements a processor's saved state holds, so no
reader refuses a snapshot for an element that it does not know. A guest that
needs the state of an element across a restore therefore needs a snapshot that
a VMM holding the element captured, and a restore by one.

The guest's speculation controls (`IA32_SPEC_CTRL`) are held by such an element;
[CPU Profiles](2.2-cpu-and-topology.md#221-cpu-profiles) says which guests have
it.

The state that guests write at boot and the processor keeps follows: the
user-wait control (`IA32_UMWAIT_CONTROL`), the debug control
(`IA32_DEBUGCTL`), the feature and power controls (`IA32_MISC_ENABLE`,
`MSR_MISC_FEATURES_ENABLES`, and `IA32_POWER_CTL`), and the machine-check state.
[Guest-Writable Processor State](2.2-cpu-and-topology.md#2214-guest-writable-processor-state)
says which guests have each. A snapshot holds an element only where the backend
that captured it can read the state, and a restore needs a backend that can
write every element that the snapshot holds. One that cannot, such as a KVM
host whose kernel does not list the MSR, refuses the restore; it does not drop
the element, because the guest would lose what it wrote. The restore checks
every element of a processor's saved state against the partition before it sets
any of that processor's state, and refuses with an error that names the first
element that the partition lacks, before any processor runs. A snapshot that was
edited can hold an element that no partition of a microVM has, such as SynIC
state, and the restore refuses it the same way.

An element can also gain a field under the same rules. The activity element,
which holds a processor's run state and its pending and blocked NMIs and
interrupts, holds the count of pending NMIs in one: KVM holds a second NMI that
reaches a processor before it has run as a second pending NMI, which the
activity's Boolean cannot hold, so the activity records the count when it is
two. KVM reports the count from Linux 6.4 on; an earlier kernel reports only
whether an NMI is pending, so a capture on it holds one. A snapshot captured
before the VMM held the field lacks it, and restoring it sets the one pending
NMI that the Boolean gives, as the earlier VMM did. A VMM that predates the
field restores a later snapshot without it, ignoring it, so a processor that
held two pending NMIs restores with one, and that guest loses an NMI the same
way. Every other snapshot restores the same on both. A restore never drops a
count that it reads: a backend that holds one pending NMI at most refuses it,
which only a damaged or crafted snapshot needs, since a snapshot restores only
on the backend that captured it.

The activity also holds an exception without a field of its own. OpenVMM does
not enable `KVM_CAP_EXCEPTION_PAYLOAD`, so KVM reports an exception that it has
queued but not injected yet as pending and injected both, and restores an
exception only as injected: a capture records it as the injected exception
alone, and a restore injects it. A snapshot that an earlier VMM captured records
it as both, and restoring it injects the exception once, as that VMM did; a VMM
that predates this restores a later snapshot's injected exception as it restored
the pair. Every snapshot restores the same on both. A restore refuses any other
pending exception, which KVM would drop and only a damaged or crafted snapshot
holds.

The activity also holds the kind of an interrupt shadow in a field of its own. A
`MOV SS` or `POP SS` leaves a shadow that lasts one instruction and also blocks
NMIs and suppresses certain debug exceptions at the next instruction boundary,
and an `STI` that finds the interrupt flag clear leaves one that does not, which
the activity's Boolean cannot say. A restore of a shadow that is given no kind
sets a `MOV SS` shadow, and a restore of no shadow sets none. The `MOV SS`
shadow is the safe one to set: an `STI` shadow that restores as a `MOV SS`
shadow holds an NMI off for one more instruction and makes an Intel CPU skip an
instruction breakpoint at that instruction, while the reverse lets an NMI or a
debug exception split a `MOV SS` from the instruction that follows it. So the
activity records the kind only for an `STI` shadow, which KVM on an Intel CPU
reports: AMD's one kind of shadow, and the interrupt state of MSHV and WHP, have
no kind to record. A snapshot captured before the VMM held the field lacks it,
and so does every snapshot whose shadow is not an `STI` shadow, which encodes as
the earlier VMM encoded it: restoring one sets a `MOV SS` shadow when it holds a
shadow, and none when it holds none, as the earlier VMM did. A VMM that predates
the field restores a later snapshot without it, ignoring it, so a processor that
held an `STI` shadow restores with a `MOV SS` shadow: the guest's NMI waits for
one more instruction, and an instruction breakpoint at that instruction, which a
`MOV SS` shadow suppresses on an Intel CPU, is lost. A restore preserves every
kind that it reads, except on KVM for an AMD CPU, whose one shadow reads back
with no kind: a backend that cannot hold the kind refuses it, which only a
damaged or crafted snapshot needs, since a snapshot restores only on the backend
and the CPU generation that captured it.

## 1.5.5 Runtime Identity

A VM's runtime identity names the runtime that launched it: a label for each of
its three runtime files, OpenVMM, the guest kernel, and the guest initramfs,
and a compatibility identity, which names the contracts that the caller speaks
with its guests. A label is an opaque token that the caller takes
from the files' install or staging metadata, such as `sha256:` and the digest
that a release's `SHA256SUMS` lists for the file: `nvx` compares labels and
never reads or digests a runtime file, which would cost time in proportion to
its size at every launch. NVX's CLI takes them from a release's `SHA256SUMS`,
or from the build provenance that a repository checkout keeps beside its
artifacts.

The compatibility identity is an opaque token too, which `nvx` compares and
never interprets: `nvx` declares no contract on the caller's behalf, since it
cannot know which contracts a caller's guests speak. The caller names its own,
such as the versions of its boot tokens and of its protocol with its guest
agent, and changes it whenever it could no longer drive a VM that it launched
under the earlier one. NVX's CLI names
`nvx-boot-v5+nvxs-v1+nvx-microvm-v2-control-v2`: the versions of its boot
contract, of the control session, and of its control contract with its bundled
guests. `nvx-rs download` checks those, and the versions that its snapshot
decoder and guest helpers read, against a release's `SOURCE-MANIFEST.json`
before it installs the release.

The runtime identity decides whether a host keeps driving a VM that it finds
recorded, as after the caller restarts or upgrades its own code. Under the same
identity, `vm::verify` returns the VM's held process, and `vm::attach`
authenticates again with the saved capability. Under another, `nvx` refuses to
drive the VM through artifacts or contracts that did not start it, with an
error of kind `RuntimeMismatch` that names the parts that differ, and only a
stop through the VM's verified process applies. A snapshot's key records the
runtime identity of its capture, so a snapshot restores only under that
identity.
