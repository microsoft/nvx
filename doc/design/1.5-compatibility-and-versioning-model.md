# 1.5 Compatibility and Versioning Model

[Architecture documentation](README.md) >
[1. Architecture Overview](1-architecture-overview.md)

Table 1.1 lists the explicit contracts that define NVX compatibility. Each
contract carries its own version or identity, independent of the others.

**Table 1.1.** Compatibility contracts.

| Contract | Governs |
| --- | --- |
| Machine ABI | CPU topology, memory layout, device topology, addresses, interrupts, transport, and guest-visible policy. |
| Boot layout | Placement and format of the Linux-direct boot structures: MP tables, bootstrap GDT and page tables, Linux boot-parameter block (zero page), and kernel command line. |
| CPU profile | Guest-visible CPU surface of one vendor and CPU generation, identified by vendor, generation, and revision, and by the digest of its canonical encoding. |
| Time ABI | Hypervisor identity, frequency interfaces, clocksources, timers, downtime semantics, and restore-time repair. The guest reads its version from the CPUID functions reserved for hypervisor information (hypervisor identity leaves). |
| Device-private schemas | Saved queue and device state that must be understood before a device can resume. |
| Snapshot format | Persisted machine contract, manifest, state inventory, memory geometry, attachment requirements, and artifact identity. |
| RAM expansion capability | Recorded RAM capacity, memory-block size, and expansion ranges that restore may activate. |
| Restore packet | Layout and meaning of the one-time record that gives a restored guest its generation, downtime, rate deviation, activation targets, fresh entropy, and a platform clone's activation record. |
| Control protocol | Authenticated sessions between the host and the guest agents, request framing, operation semantics, and lifecycle epochs. |
| Management RPC machine profile | Identity of the microVM machine profile in the management RPC. |

A change to a guest-visible address, interrupt, command-line token, feature
mask, queue shape, time rule, or device behavior requires a new contract
version. A backend-specific difference is valid only when the versioned
contract states it explicitly. A change that only widens a bound that restore
checks keeps the version: every restore that the narrower bound admitted
behaves as before, and a party that predates the change still refuses what
lies beyond its own bound. The contract then states which snapshots the wider
bound serves, and how the others fail, as
[Downtime and Continuity](3.2-clock-and-time.md#328-downtime-and-continuity)
does for the downtime bound.

Guest-visible configuration is immutable for the lifetime represented by a
snapshot. Restore derives the machine from the snapshot manifest; caller input
may reconstruct permitted external resources but cannot silently change the
captured CPU surface, memory capacity, command line, device placement, feature
masks, or network identity.

Compatibility is exact rather than best effort. Unknown versions, missing or
extra devices, changed queue shapes, incompatible CPU surfaces, malformed
state, or mismatched attachments are rejected before guest execution. A
snapshot with an unsupported manifest version must be recaptured.

## 1.5.1 Restore Compatibility

A snapshot restores only:

- On the backend that captured it.
- On a host whose CPU belongs to the generation of the snapshot's CPU profile.
- On a host whose native TSC rate lies within 250 ppm of the snapshot's
  [declared rate](3.2-clock-and-time.md#324-rates).
- With a VMM build that pins the same CPU-profile revision. No build pins a
  [host CPU profile](2.2-cpu-and-topology.md#2212-cpu-profile-selection), so
  its snapshot instead carries the only copy, which must be a valid canonical
  document with the recorded digest that the build's derivation policy would
  not change.
- With a VMM build that computes the same effective CPUID for that CPU profile
  and topology.
- With external resources that reproduce the recorded attachment identities.
- On a host whose backend can access every
  [processor state element](#154-processor-state-elements) that the snapshot
  holds.
- Within the [downtime bound](3.2-clock-and-time.md#328-downtime-and-continuity)
  of 365 days after its capture, when the snapshot's guest and the restoring
  VMM both have that bound, and otherwise within 30 days.

Released CPU-profile revisions are immutable and never deleted, so existing
snapshots stay restorable; a normative change creates a new revision.

## 1.5.2 Template Compatibility

A reusable template represents a compatibility class, not an arbitrary fleet
image. The class includes the backend, the CPU profile and generation, the
effective CPUID, the guest kernel and guest agent build, the effective command
line, device roles and geometry, network identity and policy, and consumed
layer identities. Restoring guest memory restores the captured guest agent
build, not a newly deployed initramfs, so deployments rebuild or recertify
templates on relevant rollouts.

Processor capacity and RAM geometry are immutable, but restore-time activation
lets one template serve several online processor counts and RAM sizes.
Templates are therefore keyed by capacities, base state, and supported
activation ranges. Layer-role presence and device geometry stay fixed: a
platform template accepts a substitute layer only with the same recorded
logical length and block sizes.

A template's compatibility key also records its NIC, if it has one: the
guest's address and the identity of the complete deny-all policy under which
the capture attached it. Every restore of the template replaces that policy
with its clone's own, so a template serves the clones of every network policy
at its guest's address, and its key records none of them. The key's encoding,
version 1, has not been released, so a template store that an earlier build
created is not supported: delete it and create a new one. There is no
migration.

## 1.5.3 Persisted State

The snapshot manifest is authoritative for a restored process. Native file
descriptors, sockets, named-pipe handles, and hypervisor objects are never part
of the portable state. They are recreated from stable identities and declared
reconstruction policies.

## 1.5.4 Processor State Elements

A snapshot holds each piece of a virtual processor's state as an element of its
own, and an element is optional, so a VMM can add one without a new version. A
snapshot captured before the VMM held an element lacks it, and restoring it
leaves that state at its reset value, as the earlier VMM did. A VMM that
predates an element restores a later snapshot without it, ignoring it, so it
loses that state the same way. Neither restore fails, and none of the contracts
of Table 1.1 records which elements a processor's saved state holds, so no
reader refuses a snapshot for an element that it does not know. A guest that
needs the state of an element across a restore therefore needs a snapshot that
a VMM holding the element captured, and a restore by one.

The guest's speculation controls (`IA32_SPEC_CTRL`) are held by such an element;
[CPU Profiles](2.2-cpu-and-topology.md#221-cpu-profiles) says which guests have
it.

The state that guests write at boot and the processor keeps follows: the
user-wait control (`IA32_UMWAIT_CONTROL`), the debug control
(`IA32_DEBUGCTL`), the feature and power controls (`IA32_MISC_ENABLE`,
`MSR_MISC_FEATURES_ENABLES`, and `IA32_POWER_CTL`), and the machine-check state.
[Guest-Writable Processor State](2.2-cpu-and-topology.md#2214-guest-writable-processor-state)
says which guests have each. A snapshot holds an element only where the backend
that captured it can read the state, and a restore needs a backend that can
write every element that the snapshot holds. One that cannot, such as a KVM
host whose kernel does not list the MSR, fails the restore; it does not drop the
element, because the guest would lose what it wrote.

An element can also gain a field under the same rules. The activity element,
which holds a processor's run state and its pending and blocked NMIs and
interrupts, holds the count of pending NMIs in one: KVM holds a second NMI that
reaches a processor before it has run as a second pending NMI, which the
activity's Boolean cannot hold, so the activity records the count when it is
two. KVM reports the count from Linux 6.4 on; an earlier kernel reports only
whether an NMI is pending, so a capture on it holds one. A snapshot captured
before the VMM held the field lacks it, and restoring it sets the one pending
NMI that the Boolean gives, as the earlier VMM did. A VMM that predates the
field restores a later snapshot without it, ignoring it, so a processor that
held two pending NMIs restores with one, and that guest loses an NMI the same
way. Every other snapshot restores the same on both. A restore never drops a
count that it reads: a backend that holds one pending NMI at most refuses it,
which only a damaged or crafted snapshot needs, since a snapshot restores only
on the backend that captured it.

The activity also holds an exception without a field of its own. OpenVMM does
not enable `KVM_CAP_EXCEPTION_PAYLOAD`, so KVM reports an exception that it has
queued but not injected yet as pending and injected both, and restores an
exception only as injected: a capture records it as the injected exception
alone, and a restore injects it. A snapshot that an earlier VMM captured records
it as both, and restoring it injects the exception once, as that VMM did; a VMM
that predates this restores a later snapshot's injected exception as it restored
the pair. Every snapshot restores the same on both. A restore refuses any other
pending exception, which KVM would drop and only a damaged or crafted snapshot
holds.

The activity also holds the kind of an interrupt shadow in a field of its own. A
`MOV SS` or `POP SS` leaves a shadow that lasts one instruction and also blocks
NMIs and suppresses certain debug exceptions at the next instruction boundary,
and an `STI` that finds the interrupt flag clear leaves one that does not, which
the activity's Boolean cannot say. A restore of a shadow that is given no kind
sets a `MOV SS` shadow, and a restore of no shadow sets none. The `MOV SS`
shadow is the safe one to set: an `STI` shadow that restores as a `MOV SS`
shadow holds an NMI off for one more instruction and makes an Intel CPU skip an
instruction breakpoint at that instruction, while the reverse lets an NMI or a
debug exception split a `MOV SS` from the instruction that follows it. So the
activity records the kind only for an `STI` shadow, which KVM on an Intel CPU
reports: AMD's one kind of shadow, and the interrupt state of MSHV and WHP, have
no kind to record. A snapshot captured before the VMM held the field lacks it,
and so does every snapshot whose shadow is not an `STI` shadow, which encodes as
the earlier VMM encoded it: restoring one sets a `MOV SS` shadow when it holds a
shadow, and none when it holds none, as the earlier VMM did. A VMM that predates
the field restores a later snapshot without it, ignoring it, so a processor that
held an `STI` shadow restores with a `MOV SS` shadow: the guest's NMI waits for
one more instruction, and an instruction breakpoint at that instruction, which a
`MOV SS` shadow suppresses on an Intel CPU, is lost. A restore preserves every
kind that it reads, except on KVM for an AMD CPU, whose one shadow reads back
with no kind: a backend that cannot hold the kind refuses it, which only a
damaged or crafted snapshot needs, since a snapshot restores only on the backend
and the CPU generation that captured it.
