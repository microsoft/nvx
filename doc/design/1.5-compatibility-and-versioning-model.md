# 1.5 Compatibility and Versioning Model

[Architecture documentation](README.md) >
[1. Architecture Overview](1-architecture-overview.md)

Table 1.1 lists the explicit contracts that define NVX compatibility. Each
contract carries its own version or identity, independent of the others.

**Table 1.1.** Compatibility contracts.

| Contract | Governs |
| --- | --- |
| Machine ABI | CPU topology, memory layout, device topology, addresses, interrupts, transport, and guest-visible policy. |
| Boot layout | Placement and format of the Linux-direct boot structures: MP tables, bootstrap GDT and page tables, Linux boot-parameter block (zero page), and kernel command line. |
| CPU profile | Guest-visible CPU surface of one vendor and CPU generation, identified by vendor, generation, and revision, and by the digest of its canonical encoding. |
| Time ABI | Hypervisor identity, frequency interfaces, clocksources, timers, downtime semantics, and restore-time repair. The guest reads its version from the CPUID functions reserved for hypervisor information (hypervisor identity leaves). |
| Device-private schemas | Saved queue and device state that must be understood before a device can resume. |
| Snapshot format | Persisted machine contract, manifest, state inventory, memory geometry, attachment requirements, and artifact identity. |
| RAM expansion capability | Recorded RAM capacity, memory-block size, and expansion ranges that restore may activate. |
| Restore packet | Layout and meaning of the one-time record that gives a restored guest its generation, downtime, rate deviation, activation targets, and fresh entropy. |
| Control protocol | Authenticated sessions between the host and the guest agents, request framing, operation semantics, and lifecycle epochs. |
| Management RPC machine profile | Identity of the microVM machine profile in the management RPC. |

A change to a guest-visible address, interrupt, command-line token, feature
mask, queue shape, time rule, or device behavior requires a new contract
version. A backend-specific difference is valid only when the versioned
contract states it explicitly, as it does for the virtio-net interrupt.

Guest-visible configuration is immutable for the lifetime represented by a
snapshot. Restore derives the machine from the snapshot manifest; caller input
may reconstruct permitted external resources but cannot silently change the
captured CPU surface, memory capacity, command line, device placement, feature
masks, or network identity.

Compatibility is exact rather than best effort. Unknown versions, missing or
extra devices, changed queue shapes, incompatible CPU surfaces, malformed
state, or mismatched attachments are rejected before guest execution. A
snapshot with an unsupported manifest version must be recaptured.

## 1.5.1 Restore Compatibility

A snapshot restores only:

- On the backend that captured it.
- On a host whose CPU belongs to the generation of the snapshot's CPU profile.
- On a host whose native TSC rate lies within 250 ppm of the snapshot's
  [declared rate](3.2-clock-and-time.md#324-rates).
- With a VMM build that pins the same CPU-profile revision. No build pins a
  [host CPU profile](2.2-cpu-and-topology.md#2212-cpu-profile-selection), so
  its snapshot instead carries the only copy, which must be a valid canonical
  document with the recorded digest.
- With a VMM build that computes the same effective CPUID for that CPU profile
  and topology.
- With external resources that reproduce the recorded attachment identities.

Released CPU-profile revisions are immutable and never deleted, so existing
snapshots stay restorable; a normative change creates a new revision.

## 1.5.2 Template Compatibility

A reusable template represents a compatibility class, not an arbitrary fleet
image. The class includes the backend, the CPU profile and generation, the
effective CPUID, the guest kernel and guest agent build, the effective command
line, device roles and geometry, network identity and policy, and consumed
layer identities. Restoring guest memory restores the captured guest agent
build, not a newly deployed initramfs, so deployments rebuild or recertify
templates on relevant rollouts.

Processor capacity and RAM geometry are immutable, but restore-time activation
lets one template serve several online processor counts and RAM sizes.
Templates are therefore keyed by capacities, base state, and supported
activation ranges. Layer-role presence and device geometry stay fixed: a
platform template accepts a substitute layer only with the same recorded
logical length and block sizes.

A template's compatibility key also records its NIC, if it has one: the
guest's address and the identity of the complete deny-all policy under which
the capture attached it. Every restore of the template replaces that policy
with its clone's own, so a template serves the clones of every network policy
at its guest's address, and its key records none of them. The key's encoding,
version 1, has not been released, so a template store that an earlier build
created is not supported: delete it and create a new one. There is no
migration.

## 1.5.3 Persisted State

The snapshot manifest is authoritative for a restored process. Native file
descriptors, sockets, named-pipe handles, and hypervisor objects are never part
of the portable state. They are recreated from stable identities and declared
reconstruction policies.
