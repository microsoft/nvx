## 4.3.1 Identity and Credentials

The workload runs under a host-selected, non-root numeric UID and GID fixed at
initial boot. The guest agents require an exact user and primary-group match
in the workload root and reject an unavailable identity before starting the
workload. In the layered sandbox root, each managed execution's entry checks
the account again, reading the root's user and group databases beneath its
directory descriptor, with bounds, before the workload runs. When the boot
configuration requests it, the guest agents of the blockless managed root
instead create an account for a host-selected identity that the image lacks,
and replace an image account that uses the UID with another primary group or
without a usable home. This lets a host run workloads under its own user's IDs.
The layered sandbox root creates no accounts, so it does not advertise
[account creation](4.4-host-guest-control-interface.md#442-feature-negotiation).

Before the workload starts, the guest agents clear supplementary groups and
every capability set and enable `no_new_privs`. With every capability cleared,
the workload cannot perform port I/O, so only the guest agents can request a
capture or acknowledge restore repair.

## 4.3.2 Namespaces and Mounts

In the layered sandbox root, the workload receives private mount, PID, and UTS
namespaces, in which every mount is private, and:

- A private `/proc` and a read-only `/sys`.
- A restricted `/dev`, devpts, and shared memory.
- The workload root.
- Only the live shares that the host declared.
- The workload's machine ID, bound read-only from a runtime file so that the
  guest agents can refresh it while scratch is frozen.
- The guest time status, bound read-only.

A managed execution enters through the guest library's execution entry, as the
first process of its PID namespace. The entry moves the workload root over `/`
in the execution's mount namespace rather than entering it with `chroot`
alone, gives `/dev` only its allowlisted device nodes, and makes every other
mount `nodev`. The managed agent binds the machine ID and the time status into
the workload root once, in a mount namespace of its own, of which each
execution's starts as a copy, so those binds end with the agent, before the
init agent unmounts the root. A one-shot workload's entry helper enters the
root with `chroot`.

The guest agents never pivot away from the initramfs, so they keep their own
root and stay outside the workload's namespaces, where they can supervise and
tear down the workload. The control device is never exposed inside the
workload's namespaces.

The blockless managed root has no such isolation. Each execution runs in the
guest's initramfs root, without a `chroot`, in the same mount, PID, and UTS
namespaces as the guest agents, so it sees the guest's own `/proc`, `/sys`, and
`/dev` and the host mappings bound into that root. Its
[credentials](#431-identity-and-credentials) and its
[execution cgroup](#433-cgroups-and-resources) contain it, but it has no
private mount, process, hostname, or device view.

## 4.3.3 Cgroups and Resources

In the layered sandbox root, the guest agents and workload occupy sibling
cgroups. The workload is placed in its cgroup behind a barrier before it is
released. The guest agents' cgroup carries a default memory protection of
16 MiB, a soft reservation that shields the supervisor from reclaim under
workload memory pressure but does not guarantee its survival. The workload
cgroup carries optional memory and process-count limits and is the unit of
capture freeze, termination, and descendant cleanup. When the overlay's upper
is in guest memory, the files that the workload writes into its root are
charged to the workload cgroup, so its memory limit also bounds them; see
[Layered Sandbox Root](4.1-guest-filesystem-and-image-model.md#411-layered-sandbox-root).

In the blockless managed root, each execution joins a dedicated cgroup before
the workload runs, for termination and descendant accounting. This path does
not configure a sibling guest-agent cgroup, the 16-MiB memory protection, or
the layered root's optional memory and process-count limits.

## 4.3.4 Enforcement Layers

Isolation has two enforcement layers:

- Guest policy constructs the workload's credentials, mounts, capabilities,
  and cgroups and, in the layered sandbox root, its namespaces.
- Host devices independently enforce block mutability, network policy, and
  host-filesystem access.

The guest cannot widen a host policy by remounting a filesystem, changing a
route, creating a link, or issuing a different device request.
