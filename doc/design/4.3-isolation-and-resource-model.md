# 4.3 Isolation and Resource Model

[Architecture documentation](README.md) >
[4. Guest Runtime Architecture](4-guest-runtime-architecture.md)

## 4.3.1 Identity and Credentials

The workload runs under a host-selected, non-root numeric UID and GID, one
identity for the VM, which the boot fixes, or, for a restored nvx-init, its
activation. The guest agents resolve its account once, before any execution:
nvx-init in its root's user and group databases, before it switches into the
root, and the guest's `/init` of a blockless root in the initramfs's, before
it starts the workload or the managed agent. They require exactly one user
entry with the UID, whose primary group is the GID, a group entry with the
GID, and an absolute home that is a directory, and end the VM rather than run
a workload under an identity that does not resolve. When the boot, or a
restored nvx-init's activation, requests it, they instead create an account
for an identity that the image lacks, and replace an image account that uses
the UID with another primary group or without a usable home.

Each execution takes these credentials itself, in its own child: before the
workload runs, the child clears supplementary groups and every capability
set, takes the UID and GID, and enables `no_new_privs`, so the workload keeps
none of the privileges of the guest agents and their helpers. With every
capability cleared, the workload cannot perform port I/O, so only the guest
agents can request a capture or acknowledge restore repair. `nvx` enforces
none of this:
[Run the executions](../guest-agent-guidelines.md#run-the-executions) gives
nvx-init's steps.

## 4.3.2 Namespaces and Mounts

nvx-init's space is VM-wide: one root, with one set of runtime file systems,
one hostname, machine ID and resolver file, and the host's mappings, into
which PID 1 switches once. Its executions share that root and PID 1's mount,
PID and UTS namespaces: no execution has a namespace, a root, or a hostname of
its own. The root's `/dev` holds no control device: PID 1 opens it before the
switch and keeps its descriptor, and the helpers, which run from the
initramfs, start before the switch too. Once switched, nothing unmounts the
root, and the VM ends by powering off.
[Build the space](../guest-agent-guidelines.md#build-the-space) gives the
space's rules.

The blockless managed root runs each execution in the guest's initramfs root,
in the guest agents' own namespaces, without a private mount, process,
hostname, or device view.

## 4.3.3 Priority and Resources

For nvx-init and the blockless managed root, the VM is the resource limit:
they configure no cgroups and no per-execution resource limits, such as
memory or process-count limits. nvx-init runs PID 1 and its helpers ahead of
the executions instead, with an out-of-memory score adjustment of -1000, which
exempts them from the out-of-memory killer, and a nice value of -10. Each
execution's child resets both to 0 before it takes its credentials, so that no
workload keeps them. The one limit that nvx-init sets within the VM is the
RAM upper's cap, which bounds the files that the root's upper holds in guest
memory, but not those in the runtime's own tmpfs mounts, such as `/dev/shm`,
which keep the kernel's default size; the scratch and the host's devices keep
their own storage boundaries. An execution's timeout, which its request
carries, ends the execution rather than limit its resources.

## 4.3.4 Enforcement Layers

Isolation has two enforcement layers:

- Guest policy, which the init applies and `nvx` does not enforce: the
  workload's credentials and capabilities, and the mounts of its space.
- Host devices independently enforce block mutability, network policy, and
  host-filesystem access.

The guest cannot widen a host policy by remounting a filesystem, changing a
route, creating a link, or issuing a different device request.
