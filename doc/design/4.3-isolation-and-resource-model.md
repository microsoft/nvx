## 4.3.1 Identity and Credentials

The workload runs under a host-selected, non-root numeric UID and GID, which
the boot fixes for the VM, or, for a restored nvx-init, its activation. The
guest agents require an exact user and primary-group match in the workload
root, and reject an unavailable identity before starting the workload:
nvx-init resolves the account once, before it switches into its root, and the
older layered sandbox root's entry checks it again for each execution. When
the boot configuration requests it, nvx-init and the guest agents of the
blockless managed root instead create an account for a host-selected identity
that the image lacks, and replace an image account that uses the UID with
another primary group or without a usable home. The older layered sandbox
root creates no accounts, so it does not advertise
[account creation](4.4-host-guest-control-interface.md#442-feature-negotiation).

Before the workload runs, its child clears supplementary groups and every
capability set and enables `no_new_privs`, so the workload keeps none of the
privileges of the guest agents and their helpers. With every capability
cleared, the workload cannot perform port I/O, so only the guest agents can
request a capture or acknowledge restore repair. `nvx` enforces none of this:
[Run the executions](../guest-agent-guidelines.md#run-the-executions) gives
nvx-init's steps.

## 4.3.2 Namespaces and Mounts

nvx-init's space is VM-wide: one root, with one set of runtime file systems,
one hostname, machine ID and resolver file, and the host's mappings, into
which PID 1 switches once. Its executions share that root and PID 1's mount,
PID and UTS namespaces: no execution has a namespace or a root of its own.
The root's `/dev` holds no control device: PID 1 opens it before the switch
and keeps its descriptor, and the helpers, which run from the initramfs,
start before the switch too. Once switched, nothing unmounts the root, and
the VM ends by powering off.
[Build the space](../guest-agent-guidelines.md#build-the-space) gives the
space's rules.

The older layered sandbox root gives each workload private mount, PID, and
UTS namespaces, in which every mount is private, with a private `/proc`, a
read-only `/sys`, a restricted `/dev`, the workload root, only the live shares
that the host declared, and the workload's machine ID and the guest's time
status, bound read-only. Its guest agents never pivot away from the
initramfs, so they stay outside the workload's namespaces, where they
supervise and tear down the workload, and the control device is never exposed
inside them. The blockless managed root runs each execution in the guest's
initramfs root, in the guest agents' own namespaces, without a private mount,
process, hostname, or device view.

## 4.3.3 Cgroups and Resources

For nvx-init and the blockless managed root, the VM is the resource limit:
they configure no cgroups and no per-execution limits. nvx-init runs PID 1 and
its helpers ahead of the executions, whose children give up that priority,
instead of reserving memory for them in a sibling cgroup. Its one limit
within the VM is the RAM upper's cap; the scratch and the host's devices keep
their own storage boundaries.

The older layered sandbox root keeps sibling guest-agent and workload cgroups.
The workload is placed in its cgroup behind a barrier before it is released.
The guest agents' cgroup carries a default memory protection of 16 MiB, a
soft reservation that shields the supervisor from reclaim under workload
memory pressure but does not guarantee its survival. The workload cgroup
carries optional memory and process-count limits and is the unit of capture
freeze, termination, and descendant cleanup. When the overlay's upper is in
guest memory, the files that the workload writes into its root are charged to
the workload cgroup, so its memory limit also bounds them; see
[Layered Sandbox Root](4.1-guest-filesystem-and-image-model.md#411-layered-sandbox-root).

## 4.3.4 Enforcement Layers

Isolation has two enforcement layers:

- Guest policy, which the init applies and `nvx` does not enforce: the
  workload's credentials and capabilities, the mounts of its space, and, in
  the older layered sandbox root, its namespaces and cgroups.
- Host devices independently enforce block mutability, network policy, and
  host-filesystem access.

The guest cannot widen a host policy by remounting a filesystem, changing a
route, creating a link, or issuing a different device request.
