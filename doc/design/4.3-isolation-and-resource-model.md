# 4.3 Isolation and Resource Model

[Architecture documentation](README.md) >
[4. Guest Runtime Architecture](4-guest-runtime-architecture.md)

## 4.3.1 Identity and Credentials

The init owns execution identity and privilege separation from PID 1 and its
helpers. Workloads use the selected non-root user and primary group, without
the helpers' priority or capability privileges. Empty capability sets confer
no port I/O: capture and restore repair stay on the privileged init side, not
with workloads. `nvx` parses the contracts but does not enforce the reference
init's execution policy. Its credential and launch sequence is specified in
the [guest-agent guidelines](../guest-agent-guidelines.md#own-the-executions).

## 4.3.2 Namespaces and Mounts

In nvx-init's internal reference space, the view is VM-wide: one root, runtime
filesystem set, hostname, machine ID and resolver view. It switches into that
root once; executions need no separate root entry. This reference model adds
no per-execution mount, PID or UTS namespaces. Its root's `/dev` omits the
control device; PID 1 opens that device before the switch and retains its
descriptor.

The root owns its mounts and view binds, and the init retains mapping handles
across the switch. After switching, shutdown ends the VM rather than unmounting
the root. The construction and ownership contract is in
[Construct the space](../guest-agent-guidelines.md#construct-the-space).

The retained
[layered sandbox root](4.1-guest-filesystem-and-image-model.md#411-layered-sandbox-root)
still has private execution mount, PID and UTS namespaces, with the control
device outside the workload's view. The blockless managed root instead uses
the guest's initramfs view without those execution namespaces.

## 4.3.3 Cgroups and Resources

For nvx-init's reference model, the VM is the resource limit. The init and its
helpers have priority over workload children, not a sibling cgroup reservation.
This reference model configures no cgroups or per-execution limits. Its sole
additional limit is the RAM upper's cap; scratch and host-device access keep
their own storage boundaries.

The retained layered sandbox root keeps sibling guest-agent and workload
cgroups, workload memory/PID accounting and cgroup writeback. Its soft
supervisor memory protection is not a survival guarantee. The blockless
managed root has no execution cgroup; these retained boundaries are not
replaced by the reference model.

## 4.3.4 Enforcement Layers

The init applies the guest's credentials and space contract; the library does
not enforce its workspace, capture-admission or replay obligations. Host
devices independently enforce block mutability, network policy and
host-filesystem access. Guest mounts and routing cannot widen those host
permissions.
