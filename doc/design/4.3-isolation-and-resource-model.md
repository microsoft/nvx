# 4.3 Isolation and Resource Model

## 4.3.1 Identity and Credentials

The adapter sets the workload's UID, GID, supplementary groups, and
capabilities within the guest runtime library's rules. The identity is fixed
at initial boot. Capabilities come only from this allowlist: `CHOWN`,
`DAC_OVERRIDE`, `FOWNER`, `FSETID`, `KILL`, `SETGID`, `SETUID`, `SETPCAP`,
`SETFCAP`, `NET_BIND_SERVICE`, `NET_RAW`, `SYS_CHROOT`, and `AUDIT_WRITE`.
The library refuses every other capability and gives a non-root identity no
capabilities. It always sets `no_new_privs`. The allowlist excludes
`SYS_RAWIO`, and the guest agents revoke their port-I/O permission before
starting any workload stage, so only the guest agents can request a capture
or acknowledge restore repair.

The adapter also selects the account mode. Existing-account mode requires one
passwd entry for the UID, the requested primary GID, an existing group, and
an absolute home. NVX's adapter uses this mode by default. Numeric-ID mode
uses the requested IDs without an account check. The layered root never
creates accounts; the blockless root may create one when its adapter requests
it. NVX's adapter keeps a non-root identity with no capabilities.

## 4.3.2 Namespaces and Mounts

In the layered sandbox root, each execution receives private mount, PID, and
UTS namespaces. The adapter selects the hostname; NVX's default is
`nvx-sandbox`. User namespaces remain unavailable. The entry helper makes
every mount private and provides:

- A private `/proc` and a read-only `/sys`.
- A `/dev` that contains only allowlisted device nodes, devpts, and shared
  memory.
- The workload root, moved over `/` in the execution's mount namespace, never
  entered by `chroot` alone.
- Only the live shares that the host declared.
- Either a generated per-boot machine ID, bound read-only from a runtime file
  so that the guest agents can refresh it while scratch is frozen (NVX's
  default), or the image's own `/etc/machine-id`, as the adapter chooses.
- The guest time status, bound read-only.

Every other workload-visible mount is `nodev`. For UID 0, `/proc/sys`,
`/proc/sysrq-trigger`, `/proc/bus`, `/proc/fs`, and `/proc/irq` are read-only.
`/proc/kcore`, `/proc/keys`, `/proc/timer_list`, and similar sensitive files
are masked.

The guest agents never pivot away from the initramfs, so they keep their own
root and stay outside the workload's namespaces, where they can supervise and
tear down the workload. The control device is never exposed inside the
workload's namespaces. Before entry, the helper closes old-root, control,
namespace, and process descriptors. The workload inherits no control
terminal.

The blockless managed root has no such isolation. Each execution runs in the
guest's initramfs root, without a `chroot`, in the same mount, PID, and UTS
namespaces as the guest agents, so it sees the guest's own `/proc`, `/sys`, and
`/dev` and the host mappings bound into that root. Its
[credentials](#431-identity-and-credentials) and its
[execution cgroup](#433-cgroups-and-resources) contain it, but it has no
private mount, process, hostname, or device view.

## 4.3.3 Cgroups and Resources

In the layered sandbox root, the guest agents and workload occupy sibling
cgroups. The workload is placed in its cgroup behind a barrier before it is
released. The guest agents' cgroup carries a default memory protection of
16 MiB, a soft reservation that shields the supervisor from reclaim under
workload memory pressure but does not guarantee its survival. The workload
cgroup carries optional memory and process-count limits and is the unit of
capture freeze, termination, and descendant cleanup. In a managed lifecycle,
each execution's cgroup is a child of the workload cgroup, so those limits and
the capture freeze cover every execution.

In the blockless managed root, each execution joins a dedicated cgroup before
the workload runs, for termination and descendant accounting. This path does
not configure a sibling guest-agent cgroup, the 16-MiB memory protection, or
the layered root's optional memory and process-count limits.

## 4.3.4 Enforcement Layers

Isolation has two enforcement layers:

- Guest policy constructs the workload's credentials, mounts, capabilities,
  and cgroups and, in the layered sandbox root, its namespaces.
- Host devices independently enforce block mutability, network policy, and
  host-filesystem access.

The guest cannot widen a host policy by remounting a filesystem, changing a
route, creating a link, or issuing a different device request.
