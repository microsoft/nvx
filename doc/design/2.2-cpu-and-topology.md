## 2.2.1 CPU Profiles

The guest sees a CPU profile rather than host passthrough. A CPU profile is
the complete guest-visible CPU surface of one vendor and CPU generation,
shared by every backend. In every governed CPUID entry the guest sees only
CPU-profile values, except for a fixed set of VMM-owned fields and the fields
that the time ABI owns. One CPU profile gives the same guest behavior on every
backend; it does not make snapshots portable across backends.

A CPU profile is versioned data with one canonical encoding and a SHA-256
digest. Its identifier has the form `<vendor>.<generation>.v<revision>`. It
contains:

- The CPU vendor and the generation's CPU signatures, as ranges of the
  numbers that identify a processor design and its revision (family, model,
  and stepping).
- A dense CPUID table covering every basic and extended leaf and each leaf's
  secondary indexes (subleaves) up to the CPU profile's maxima, with a value
  and a mask per register, where a set mask bit pins the value and a clear bit
  marks a VMM-owned or runtime-owned bit.
- The extended processor state save and restore (XSAVE) components that the
  guest may enable, such as vector registers, with each component's size,
  offset, and flags.
- The guest physical address width.
- Pinned model-specific register (MSR) values with masks.
- Informative provenance.

CPU profiles are derived by intersecting host fingerprints per register, first
within each backend and then across backends. Released revisions are
immutable and never deleted; a normative change creates a new revision.

As Table 2.3 shows, every CPUID bit has exactly one owner.

**Table 2.3.** Ownership of CPUID fields.

| Owner | Fields |
| --- | --- |
| CPU profile | Every governed value whose mask bit is set, and pinned MSRs |
| VMM | Logical processor count and initial APIC ID, the bit that advertises the APIC's MSR-based mode (x2APIC), core and cache-sharing counts, and the processor topology leaves |
| Guest runtime state | Bits that report whether the guest kernel has enabled XSAVE and memory protection keys (`OSXSAVE` and `OSPKE`), and the XSAVE sizes for the current values of the registers that select the enabled user and supervisor state components (XCR0 and XSS) |
| Time ABI | Leaves `0x40000000` through `0x4fffffff`, `0x15`, `0x16`, and the [CPU time bits](3.2-clock-and-time.md#323-cpu-time-bits) |
| Policy | Zeros for virtualization extensions, but VMX under [nested virtualization](#2214-nested-virtualization), Intel's secure enclaves (SGX), processor trace, cache and memory-bandwidth allocation (resource director technology), memory encryption, and other excluded features |

Because the machine has one socket and one core per virtual processor, every
cache reports the processor count less one as its cores per socket, the L3
cache is shared by every processor, and each L1 and L2 cache serves one
processor.

### 2.2.1.1 Effective CPUID

The effective CPUID is a pure function of the CPU profile, the VM topology,
the time ABI's identity leaves, and whether the VM has
[nested virtualization](#2214-nested-virtualization). It lists exactly the
governed entries:
every leaf and subleaf of the CPU profile's table; the topology leaves at the
subleaves that the topology defines, plus the subleaf that terminates them;
and the hypervisor identity leaves with their explicit zero leaves. The VMM
computes it, records it in the snapshot manifest, and recomputes it on
restore. The record therefore never depends on how a backend enumerates or
caches CPUID, and one CPU profile and topology produce the same record on
every backend. Because the record also fixes the VMM's own leaves and
VMM-owned bits, changing how the VMM computes them breaks snapshot
compatibility.

Entries that only probing past an advertised maximum reaches are reserved:
leaves above the maximum basic or extended leaf, subleaves past a leaf's
maximum or terminator, and XSAVE subleaves of disabled components. Their
values are implementation-defined, and guests must not rely on them;
verification still keeps host features out of them.

Some fields are informational and are not compared: the processor name that
CPUID reports (the brand string) is generic per generation and names no
frequency, cache descriptor leaves come from reference hosts, and the
microcode revision is not pinned.

Mitigation-relevant bits follow the hardware. A CPU profile claims an immunity
or a control only if every CPU of its generation has it and every backend can
present it, so guests keep their mitigations enabled.

### 2.2.1.2 CPU Profile Selection

Every microVM has a CPU profile. A cold boot selects a pinned CPU profile
explicitly, selects one automatically, or uses a host CPU profile:

- Automatic selection uses the highest revision of the single pinned profile
  whose generation covers the host's vendor, family, model, and stepping.
- On an Intel or AMD CPU that no pinned profile serves, automatic selection
  falls back to a host profile and warns at every cold boot that takes the
  fallback.
- A CPU of another vendor, an ambiguous catalog match, or a pinned profile
  that the backend cannot support fails instead of falling back.

A host CPU profile is derived at cold boot from a fingerprint of the backend
on the current host, under the same derivation policy as the pinned profiles.
The guest still sees a policy-filtered surface rather than host CPUID: only
permitted data leaves keep data, policy features are cleared, XCR0 stays
within the permitted components, the brand string is generic, and the
generation covers only the host's family, model, and stepping. A host profile
is neither reviewed nor immutable, because firmware, microcode, hypervisor, or
operating-system updates can change it. Its snapshots carry the host
profile's document and restore only on a host of the same CPU model and
stepping whose hypervisor supports it.

A restore always uses the CPU profile that the snapshot records and never
falls back.

### 2.2.1.3 CPU Profile Verification

At partition creation, for cold boot and restore, the VMM verifies that:

1. The CPU profile is valid, including its canonical encoding, density,
   ownership masks, and CPU time bits.
2. The host's vendor, family, model, and stepping belong to the CPU profile's
   generation.
3. The backend supports the CPU profile, including every set feature bit,
   every limit, the XSAVE layout, the XCR0 and XSS subsets, and every pinned
   MSR value, with the time policy bits exempt.
4. On restore, the VMM pins the same CPU profile ID and digest, or the
   recorded host profile is a valid canonical document with the recorded
   digest, and the recomputed effective CPUID equals the recorded one.
5. The backend presents the effective CPUID on the first virtual processor
   under its masks.
6. On backends that pass reserved entries through, no nonzero entry exists
   outside the CPU profile's tables, the identity range, and the topology
   leaves.

Every violation is reported together, naming the leaf, subleaf, register, and
bit.

### 2.2.1.4 Nested Virtualization

Nested virtualization is an attribute of microVM ABI 3 that a cold boot
requests explicitly: OpenVMM's `--nested-virt` with the microVM machine, the
management RPC's `VMConfig.nested_virt`, and `nvx-rs run --nested-virt`. It is
off by default, and a VM without it is the machine that the rest of this guide
describes, unchanged. A VM with it exposes Intel's hardware virtualization,
VMX, so that its guest runs VMs of its own:

- **Effective CPUID.** VMX, `CPUID.1:ECX[5]`, is set over the CPU profile's
  pinned zero, which the policy row of Table 2.3 otherwise keeps. It is the
  only change: the CPU profile and its digest stay the same, and the identity
  leaves stay those of [Hypervisor Identity](3.2-clock-and-time.md#321-hypervisor-identity),
  so that leaf `0x4000000a` still reads zero, offering no enlightened VMCS or
  other Hyper-V nesting feature. The capability MSRs that describe the VMX
  controls that a guest hypervisor may use, and `IA32_FEATURE_CONTROL`, are
  the backend's, an explicit backend-specific difference of the contract:
  KVM's nested VMX and WHP's nested virtualization offer different controls,
  which the guest's hypervisor discovers.
- **Vendors.** No CPU profile describes AMD's SVM, whose feature leaf
  `0x8000000a` a guest hypervisor reads, so an AMD CPU profile refuses nested
  virtualization with `E_PROFILE_UNSUPPORTED` rather than exposing SVM.
- **Backends.** KVM gives it where its `kvm_intel` offers nested VMX, and
  refuses the VM otherwise. WHP gives it where it offers nested
  virtualization in its processor features, which the partition requests
  before the time ABI configures its features, and refuses the VM otherwise.
  MSHV offers nested virtualization only to a partition with the Hyper-V guest
  interface, which the [time ABI](3.2-clock-and-time.md) excludes, so the
  machine profile refuses it on MSHV before the VM is created. Every refusal
  happens before the guest runs.
- **Snapshots.** The microVM's saved state holds no processor state of a
  nested guest: KVM's backend cannot save it, MSHV refuses it, and the
  saved-state contract does not include WHP's. A VM with nested
  virtualization is therefore never captured or restored, and the machine
  refuses both before the VM starts: the command line and the management RPC
  refuse a snapshot destination or a restore beside the request, the worker
  refuses a restore that asks for it, and a capture request reaches no
  quiesce. A snapshot never has nested virtualization, so the snapshot format,
  the manifest, and the saved-state schemas are unchanged, and a VM with
  nested virtualization never shares a snapshot or a template with one
  without it. A recorded effective CPUID that set VMX would not equal the one
  that a restore recomputes anyway.
- **Guest.** The guest kernel builds KVM with Intel's support (see
  [Build](../build.md)), which initializes only where VMX is exposed: the
  guest of a VM without nested virtualization has no `/dev/kvm`. When KVM
  initializes, it reads `IA32_XSS`, which the KVM and WHP backends serve, as
  the CPU profile's `XSAVES` requires.
- **Sandboxes.** The guest agents give a sandbox's workload `/dev/kvm` exactly
  when the guest has it, with the ownership and resources that
  [Isolation and Resource Model](4.3-isolation-and-resource-model.md#432-namespaces-and-mounts)
  describes.

Nested virtualization expands the attack surface of the host; see
[Trust Boundaries](1.4-trust-boundaries.md#146-nested-virtualization).
Benchmarks never request it, and their results never mix with those of VMs
with it (see [Benchmarks](../benchmarks.md)).

## 2.2.2 Processor Capacity

Processor capacity is part of machine identity and stays fixed for the life
of a VM. The processor topology, APIC IDs, MP tables, and saved processor
inventory always describe exactly the capacity, even when a snapshot captures
fewer online processors, so bringing more processors online at restore never
changes the topology.
[Processor Activation](5.5-restore-protocol.md#553-processor-activation)
describes how a restore selects its online processors.
