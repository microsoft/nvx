# 2.1 Machine Model and Configuration

[Architecture documentation](README.md) >
[2. Virtual Machine Architecture](2-virtual-machine-architecture.md)

The machine profile is selected explicitly and owns all guest-visible
configuration. Machine identity is never inferred from a kernel, device, or
hypervisor choice: every frontend, including the command line, the management
RPC, and snapshot configuration, carries it to the VM worker. Validation occurs
before host resources are opened and again at the worker boundary.

The current machine profile's architectural invariants are:

- An x86-64 guest with Linux direct boot and Intel MP 1.4 tables, without firmware.
- One NUMA node.
- One socket, one die, one core per virtual processor, no SMT, and xAPIC mode.
- 1, 2, 4, or 8 virtual processors with contiguous APIC IDs starting at zero.
- A fixed low-memory boot layout and a fixed 3-to-4-GiB MMIO aperture.
- The [time ABI](3.2-clock-and-time.md) as the only time path, with one CPU profile.
- A fixed chipset and virtio-mmio device topology.
- No VTL2, confidential-VM isolation, or nested virtualization.
- No paravirtual features from the backend's hypervisor, such as Hyper-V
  enlightenments or the KVM paravirtual clock. The time ABI's minimal
  hypervisor identity, the same on every backend, is the only hypervisor
  interface.

## 2.1.1 Allowlisted Platform

The machine profile constructs the required machine directly instead of creating a standard PC and
removing unwanted devices.

It rejects firmware and boot interfaces: UEFI, PCAT, IGVM, and caller-supplied ACPI, SMBIOS, and
device trees. It also rejects PCI and PCIe, vPCI, VMBus, the DMA controller of the legacy ISA
expansion bus (ISA DMA), IDE, floppy, VMGS, graphics, VGA firmware, debugger resources, and every
device outside the machine profile. The machine profile itself emits the fixed Linux direct
MP-table metadata.

## 2.1.2 Configuration Ownership

Table 2.1 lists the owner and lifetime of each kind of configuration. A
lifetime is one of:

- **Contract version.** The same for every VM of one machine-contract version.
- **VM.** Fixed at cold boot, recorded in every snapshot, and restored from it
  unchanged.
- **VM process.** Bound at cold boot and again at every restore, matching the
  identities that the VM recorded.
- **Restore.** Selected for each restore, within the limits that the snapshot
  records.

**Table 2.1.** Configuration ownership and lifetime.

| Configuration | Owner | Lifetime |
| --- | --- | --- |
| Boot layout, device placement, interrupts, and feature masks | Machine profile | Contract version |
| Processor capacity, base RAM and optional RAM capacity, and CPU profile | Host, validated by the machine profile | VM |
| Effective kernel command line | Machine profile, from host policy and caller arguments | VM |
| Workload identity and lifecycle | Host | VM |
| Console, network, block, and host filesystem devices, with their identities and policies | Host | VM |
| Host attachments: console endpoints, the network endpoint, block files, and exported host directories | Host, matching the recorded identities | VM process |
| Online processor and RAM activation targets | Host, within snapshot limits | Restore |

The host fixes the workload policy of a fresh boot. An optional nonzero
numeric UID and GID become the fixed workload identity, and an optional
one-shot or managed lifecycle selects whether the guest agents run one
workload or stay resident for sequential requests over the control console.
Both are command-line tokens that the machine profile owns and that caller
arguments cannot supply. A managed lifecycle requires a fixed workload
identity and a live, authenticated control console.

## 2.1.3 Storage Configuration

Sandbox storage uses block devices with fixed roles rather than arbitrary
disks. The roles are the layers of the sandbox root filesystem: a read-only
`distro` lower layer for the base operating system, beneath one writable
`scratch` layer that holds the sandbox's private changes.
[Block Storage](3.4-block-storage.md) describes each role.

A disk without a role is rejected, and a disk-backed topology ends with
writable scratch. The only exception is the RAM-backed overlay layout, which
requires exactly one read-only `distro` block and no scratch, keeps the
guest's overlay upper layer in RAM, on a tmpfs that the guest agents mount
(see [Layered Sandbox Root](4.1-guest-filesystem-and-image-model.md#411-layered-sandbox-root)),
and supports neither capture nor restore.
Snapshot capture with blocks requires a read-only `distro` layer followed by
writable scratch, both backed by cached, regular raw files with nonzero,
512-byte-aligned geometry. Blockless machines are also snapshot-capable and
carry no sandbox tier metadata.

Host filesystem sharing uses the fixed filesystem slot rather than adding
devices. The slot exports one host directory, or an aggregate of named
directory or regular-file children, each with its own access mode, beneath a
read-only synthetic root.

## 2.1.4 Restore-Time Configuration

Restore is stricter than cold boot. Guest-visible configuration is read from
the snapshot's machine contract. Restore-time input may only:

- Select the backend kind that the snapshot records.
- Supply required attachments.
- Bind a new directory export to a captured dormant filesystem slot, when the
  snapshot records that capability.
- Select processor and RAM activation targets that the contract allows.

These process-local inputs never change processor capacity, RAM capacity, the
command line, device placement, feature masks, or filesystem and network
identity. Restore always uses the snapshot's CPU profile and never falls back.
Because the captured command line fixes network addressing, workload identity,
and lifecycle, restore rejects inputs that would change them, and a supplied
processor count may only repeat the captured capacity.

## 2.1.5 Execution Backends

The execution backend is a property of the host process, not of the guest
platform. Backend code supplies partition creation, virtual processor
execution, memory registration, and interrupt injection while preserving the
same guest-visible contract. KVM and MSHV run on Linux hosts, and WHP runs on
Windows hosts.
