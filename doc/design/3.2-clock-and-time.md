# 3.2 Clock and Time

[Architecture documentation](README.md) >
[3. Virtual Devices](3-virtual-devices.md)

The NVX time ABI is the single guest-visible time, timer, and clock contract
on every backend and launch path. It is versioned independently of the
machine ABI. Every rule is a hard check: a host or snapshot that cannot meet
the contract is rejected with a stable error code, a guest that observes a
violation fails fast, and no rule falls back to another behavior.

The time ABI applies the [architecture goal](1.1-goals.md)
of keeping the guest-visible machine independent of the selected hypervisor to
clocks and timers. It provides:

- The same CPUID identity, synthetic MSRs, CPU time bits, clocksource, tick,
  timers, and restore semantics on every backend and launch path.
- No guest kernel patches and no clock parameters on the kernel command line.
- Restore within one backend across hosts of the same CPU generation and CPU
  profile whose TSC rates match within a small tolerance, including after a
  host reboot.
- Guest monotonic time that advances by the snapshot downtime, and a wall
  clock that is set on every restore and disciplined afterwards.
- Kernel stall, lockup, clocksource, and TSC-warp detectors that never trip
  across capture and restore.

The guest sees:

- A TSC that ticks at a constant rate in every processor power and frequency
  state (an invariant TSC) as its only clocksource.
- The declared TSC and LAPIC timer rates through a minimal synthetic
  hypervisor identity.
- A one-shot LAPIC timer at the backend's fixed rate.
- A PIT that the guest disables at boot.
- A programmable RTC anchored to UTC.

An invariant TSC keeps one rate on a given host; it does not give every host
the same rate. The guest TSC runs at its host's native rate, which can differ
between hosts of one CPU generation and is not part of the CPU profile, so the
guest reads the declared rate from a frequency MSR instead of deriving it from
CPUID. A cold boot declares its host's rate, and a snapshot restores only on a
host whose rate lies within 250 ppm of that declaration; see
[Rates](#324-rates).

Table 3.4 lists the notation that the time ABI uses.

**Table 3.4.** Time ABI notation.

| Symbol | Meaning |
| --- | --- |
| `F` | Declared guest TSC rate in Hz |
| `F_s` | Declared rate recorded in a snapshot |
| `F_d` | Native TSC rate of the destination partition in Hz |
| `L` | LAPIC timer rate in Hz |
| `C` | Processor capacity of the machine |
| `D` | Snapshot downtime in nanoseconds |
| `T_c` | Guest TSC of the first processor at the capture anchor |
| `Q` | Host monotonic time from the VM-time cut at quiesce to the capture anchor |
| `g` | Restore generation counter of a VM process |

## 3.2.1 Hypervisor Identity

As Table 3.5 shows, every processor sees a minimal Hyper-V frequency and
invariant-TSC identity, configured identically on every backend. Each row
lists the values that one leaf returns in the four general-purpose registers
through which CPUID reports its results (EAX, EBX, ECX, and EDX).

**Table 3.5.** Hypervisor identity leaves.

| Leaf | EAX | EBX | ECX | EDX |
| --- | --- | --- | --- | --- |
| `0x40000000` | `0x40000005` (maximum leaf) | `0x7263694d` (`"Micr"`) | `0x666f736f` (`"osof"`) | `0x76482074` (`"t Hv"`) |
| `0x40000001` | `0x31237648` (`"Hv#1"`) | 0 | 0 | 0 |
| `0x40000002` | `0x0058564e` (`"NVX"`) | `0x00020000` (time ABI 2.0) | 0 | 0 |
| `0x40000003` | `0x00008860` | 0 | 0 | `0x00000100` |
| `0x40000004` | 0 | `0xffffffff` | 0 | 0 |
| `0x40000005` | `C` | `C` | 0 | 0 |

Leaf `0x40000003` grants exactly the privileges that Linux needs to detect the
platform, hypercall-MSR and virtual-processor-number (VP-index) access, plus
frequency-register and invariant-TSC-control access, and advertises only the
frequency registers.
Leaf `0x40000004` recommends nothing and never requests spinlock notification.
Leaves `0x40000006..0x4000000f` and `0x40000080..0x40000082` read as explicit
zeros. Every other leaf in `0x40000006..0x400000ff` returns either zeros or
the vendor's architectural out-of-range result, and no base from `0x40000100`
through `0x4000ff00` carries a hypervisor signature, so Linux selects only the
Hyper-V platform. Beyond the leaves of Table 3.5, no leaf returns Hyper-V
feature data, and leaf `0x40000081` carries no `VS#1` virtualization-stack
interface signature.

The identity deliberately deviates from the Hyper-V specification:

- The hypercall MSRs raise a general-protection fault (#GP), there is no
  hypercall page, and hypercall instructions are outside the contract.
- The TSC frequency MSR returns the declared rate `F`, which may differ from
  the physical rate by up to the [rate tolerance](#324-rates) after a restore.
- The invariant-TSC control can be cleared after it is set.
- The invariant-TSC CPUID bit is set from boot rather than after the control
  is written.
- Leaf `0x40000002` carries an NVX signature and the time ABI version instead
  of a build number.
- Leaf `0x40000005` reports the processor capacity.

The guest's only side effect is selecting the Hyper-V platform. No paravirtual
clock, interrupt, TLB, spinlock, steal-time, or page-fault feature exists on
any backend, and the scheduler clock and vDSO use the raw TSC.

## 3.2.2 MSRs

As Table 3.6 shows, the VMM serves the identity MSR range
`0x40000000..0x400001ff` identically on every backend.

**Table 3.6.** Identity MSRs.

| MSR | Name | Read | Write |
| --- | --- | --- | --- |
| `0x40000002` | VP index | Processor index | #GP |
| `0x40000022` | TSC frequency | `F` | #GP |
| `0x40000023` | APIC frequency | `L` | #GP |
| `0x40000118` | TSC invariant control | Last value written; 0 after reset | 0 or 1 accepted; any other value #GP |
| Any other MSR in the range | | #GP | #GP |

The TSC invariant control is one partition-wide value. It is guest state,
saved and restored with the VM. Linux writes 1 once at boot without fault
handling, so that write must never fault on any backend.

The MSRs that hold an offset added to the processor's TSC (`IA32_TSC_ADJUST`,
`0x3b`) and the TSC value at which the LAPIC timer fires in TSC-deadline mode
(`IA32_TSC_DEADLINE`, `0x6e0`) raise #GP on every backend, as do the
cache-control registers of Intel's P6 processor generation (the legacy P6
L2-cache MSRs).

As Table 3.7 shows, under an AMD CPU profile, the VMM also serves two
configuration MSRs with fixed values.

**Table 3.7.** AMD configuration MSRs.

| MSR | Name | Read | Write |
| --- | --- | --- | --- |
| `0xc0010015` | Hardware configuration (`HWCR`) | `0x1000000`: only the bit that makes the TSC count at a fixed frequency (`TscFreqSel`) | The value read changes nothing; any other value #GP |
| `0xc0011029` | Decode configuration (`DE_CFG`) | `0x2`: only the bit that makes the load-fence instruction hold later instructions until earlier ones complete (`LFENCE` serialization) | The value read changes nothing; any other value #GP |

**Table 3.8.** CPU time bits.

| --- | --- | --- |

| `0x1` | ECX[24] TSC-deadline timer | 0 |
| `0x1` | ECX[15] performance and debug capabilities MSR (PDCM) | 0 |
| `0x1` | EDX[4] TSC | 1 |
| `0x6` | EAX, EBX, ECX, EDX | `0x00000004` (only the always-running APIC timer, ARAT), 0, 0, 0 |

Leaves `0x15` and `0x16` are zeroed rather than synthesized. Linux takes both
rates from the frequency MSRs, which keeps the CPU profile's CPUID independent
of any host's rate. The invariant-TSC bit is policy rather than a
fingerprinted feature: every CPU profile sets it, and every backend presents
it.

## 3.2.4 Rates

The guest TSC runs at the destination's native rate `F_d` and is never scaled.
The declared rate `F` is fixed for the life of a snapshot lineage: a cold boot
declares its native rate, and every restored process keeps `F = F_s`. The
kernel computes its TSC frequency once and never recalibrates.

At restore, the native rate must lie within 250 ppm of the declared rate,
computed with integer arithmetic of at least 128 bits:

```text
accept  iff  |F_d - F_s| * 1_000_000  <=  250 * F_s
```

The boundary is accepted. The manifest records the tolerance, and any other
recorded value is rejected. Within the tolerance, the TSC is neither scaled
nor trapped, the frequency MSR keeps returning `F_s`, and guest clocks run
fast or slow by at most the deviation. The restore packet reports that
deviation in the kernel's frequency-adjustment unit, ppm scaled by 2^16, and
the host clock correction of every [time sample](#329-time-samples) includes
it, so that the guest compensates it from its repair on:

```text
rate_deviation = round((F_d - F_s) * 1_000_000 * 65_536 / F_s)
```

Every rate must also be plausible, `500 MHz <= F <= 10 GHz`. A backend that
cannot report its native rate is rejected at cold boot, capture, and restore
alike; there is no calibration fallback.

The LAPIC timer rate `L` is a backend constant: 1 GHz on KVM and 200 MHz on
MSHV and WHP. The kernel presets its timer period from the APIC frequency MSR
and never calibrates the LAPIC. On restore, the destination's rate must equal
the recorded rate exactly.

## 3.2.5 Clocksource, Tick, and Timers

With this identity, the guest kernel takes the TSC rate from the frequency
MSR, trusts the TSC as reliable, which disables the clocksource watchdog and
the CPU-online warp test, presets the LAPIC timer period, and disables the PIT
at boot. The booted guest must then be in this state:

- Every CPU reports a constant, nonstop, known-frequency, reliable TSC with
  RDTSCP and ARAT, and none reports a TSC-deadline timer or `TSC_ADJUST`.
- The TSC is the current clocksource and, after each CPU's first tick, the
  only available one.
- Ticks are tickless-idle with high-resolution timers, and every online CPU's
  tick device is the LAPIC timer in one-shot mode.
- No PIT, high-precision event timer (HPET), or broadcast clock-event device
  exists.
- The LAPIC timer is never periodic and never in TSC-deadline mode after boot.
- PIT channel 0 never counts after boot, and IRQ 0 has no timer handler.

Capture and restore reject an armed periodic or TSC-deadline LAPIC timer and a
periodically counting PIT channel 0. Across a downtime `D`, a counting
one-shot LAPIC timer advances by exactly:

```text
ticks = floor(D * L / 1_000_000_000 / divide)
```

where `divide` is the timer's divide configuration. If `ticks` reaches the
current count, the count becomes zero and the timer interrupt is queued unless
the LAPIC register that configures it (its LVT entry) is masked; otherwise,
the count decreases by `ticks`. A queued or pending vector must reach its
processor when the processor is released, even if it is halted.

## 3.2.6 Backend Obligations

Each backend implements the same obligations behind one VMM interface. The
guest-visible result is identical; only the mechanism differs. Every backend
must:

- Present exactly the identity leaves and their explicit zero leaves, with no
  other hypervisor signature.
- Present the CPU profile's effective CPUID, including the CPU time bits.
- Route the identity MSRs, and under an AMD CPU profile the two configuration
  MSRs, to the VMM.
- Report the native TSC rate and never scale the TSC.
- Run the LAPIC timer at the backend's fixed rate.
- Deliver a pending LAPIC vector after a LAPIC state write, even to a halted
  processor.
- Hide the TSC-deadline timer and `TSC_ADJUST`, and fault both MSRs.
- Expose the invariant TSC.
- Offer no paravirtual or synthetic features, and never enable a
  hypervisor-specific emulator or its saved state.
- Pair the first processor's TSC with a host time sample within 100 µs for
  the capture anchor, keeping the tightest of at most 64 samples.
- Know the guest TSC's offset from the host TSC before any processor runs, at
  cold boot and at every restore, so that the VMM pairs each
  [time sample](#329-time-samples)'s host UTC with the guest TSC.
- Set every instantiated processor's TSC at one host instant and verify it by
  read-back before any processor runs.
- Keep live cross-processor skew within 1 µs after release.

## 3.2.7 Cross-Processor Consistency

At every guest-observable instant, the TSCs of any two online processors
differ by at most 1 µs, that is `F_s / 1,000,000` cycles. The guest kernel no
longer checks TSC consistency, so the bound is enforced outside the guest.
Cold boot starts every processor's TSC together. Restore writes one target to
every instantiated processor at one host instant and verifies it by read-back,
so the VMM introduces no skew of its own. After release, each backend keeps
live skew within the bound, and a host that cannot hold it does not qualify
for the contract.

## 3.2.8 Downtime and Continuity

Guest monotonic time advances by the downtime `D`, the host time elapsed
between the capture anchor and the restore anchor, plus at most the restore
latency `R` from the restore anchor to the first restored instruction. The
guest observes no other discontinuity between the snapshot request and the
first restored instruction.

The capture anchor records:

- `T_c`, the first processor's guest TSC.
- Host UTC in nanoseconds since the Unix epoch.
- Suspend-inclusive host monotonic time.
- The host identity.
- The host boot identity.

A host that cannot provide all of them rejects capture and restore.
As Table 3.9 shows, restore takes the same sample at its own anchor and
selects exactly one downtime source.

**Table 3.9.** Downtime source selection.

| Condition | Source | `D` |
| --- | --- | --- |
| Same host identity, boot identity, and host clock kind | Host monotonic time | `monotonic_now - monotonic_capture` |
| Anything else | Host UTC | `utc_now - utc_capture` |

`D` must satisfy `0 <= D <= 30 days`. On the monotonic path, a UTC delta that
differs from `D` by more than one second is reported as a host wall-clock step
and does not change `D`. The restore packet reports the selected source.

VM time, the clock of the VMM's emulated devices, and the RTC stop at quiesce,
before the capture anchor. Capture therefore records `Q`, the host monotonic
interval from that cut to the anchor, and restore advances VM time and the RTC
by `D + Q` so that they resume in step with the guest TSC, which kept running
through `Q`. The TSC, the LAPIC timers, and the restore packet use `D`.
`D + Q` must not exceed 30 days. `Q` is best effort: a snapshot without it
restores with `Q = 0` and a warning.

The restore anchor is the instant of the synchronized TSC set, and guest time
runs from that instant on every backend; no backend defers it to the first
processor run. No backend stops guest time for a capture either, so a capture
that rolls back leaves the guest's clocks continuous, and the guest sees the
quiesce as elapsed time, as it would a long preemption.

## 3.2.9 Time Samples

Figure 3.1 shows the layout of the 48-byte sample that writing `0xa7` to the
byte-channel selector latches into the time window. The VMM takes the sample
while it handles the selector write: it reads host UTC, pairs it with the
guest TSC, and reads how the host's time service disciplines host UTC.

```text
offset size field
     0    1 version = 2
     1    1 flags                bit 3 mirrors the restore packet's override flag; other bits zero
     2    1 status               host UTC: 0 unknown, 1 synchronized, 2 free-running, 3 unreliable
     3    1 reserved = 0
     4    4 generation           u32, little-endian, g of this VM process
     8    8 utc_ns               u64, little-endian, host UTC at the latch
    16    8 tsc                  u64, little-endian, guest TSC at the instant of utc_ns
    24    4 pairing_ns           u32, little-endian, bound on the distance of those instants
    28    4 disruption           u32, little-endian, changes with each host clock disruption
    32    8 correction           i64, little-endian, ppm scaled by 2^16
    40    4 correction_bound     u32, little-endian, ppm scaled by 2^16, 0xffffffff if unknown
    44    4 max_error_us         u32, little-endian, 0xffffffff if unknown
```

**Figure 3.1.** Time-sample layout.

The guest TSC is never scaled, so it is the host TSC plus an offset that is
fixed for the life of a VM process. The backend reads that offset, or
measures it by bracketing a read of the first processor's TSC with host TSC
reads, before any processor runs, at cold boot and at every restore. Each
sample brackets a read of host UTC with host TSC reads, keeping the tightest
of up to 16 brackets, and converts the host TSC to the guest TSC with the
offset. `pairing_ns` adds the offset's uncertainty to half the bracket.

`correction` is how fast host UTC runs against the guest TSC counted at the
declared rate `F`, minus one, in the kernel's frequency-adjustment unit:

```text
correction = (1 + c_os) * F / F_d - 1
```

where `c_os` is the time service's correction of the host clock against the
TSC at the native rate `F_d`. On Linux, it is the frequency and tick that
`adjtimex` reports. On Windows, `GetSystemTimeAdjustmentPrecise` reports the
performance counter's frequency as its increment, and the counter's ticks in
each second of host UTC as its adjustment, so `c_os` is the increment over the
adjustment, minus one, while a time service adjusts the clock, and zero
otherwise. After a restore, `F` is `F_s`, so the correction includes the
restore's rate deviation.
`correction_bound` bounds the correction's error: 1 ppb of rounding when the
host clock and `F_d` come from one calibration, as with Linux's `tsc`
clocksource and KVM, or Hyper-V's reference TSC and MSHV or WHP; the kHz to
which one of them is known otherwise; and unknown when the host clock may not
follow the TSC.

`status` is the host's own account of its clock. On Linux, `adjtimex`
reports a clock fault as unreliable and an unsynchronized clock as
free-running; on Windows, a clock that no time service adjusts is
free-running. `max_error_us` is the maximum error that Linux's time service
sets, and unknown on Windows. `disruption` starts at zero in each VM process
and changes when the host resumes from a suspension, when the guest TSC's
offset from the host TSC changes, and when host UTC steps between two samples.
OpenVMM measures host UTC's advance against the host's monotonic clock, so the
smallest step that changes the counter depends on the host OS. Linux's
`CLOCK_BOOTTIME` runs at host UTC's corrected rate, so a step of 1 ms or more
changes it. Windows' interrupt time runs uncorrected, and the host's correction
may have changed since the previous sample, so a step changes it only when it
departs from what the latest correction explains by at least 1 ms plus 500 ppm
of the time since that sample: 33 ms at the discipline's 64-second cadence.
The discipline slews or steps a smaller step at its next poll like any other
offset, without returning to its fast cadence.

These values feed only the guest's wall-clock discipline. The TSC stays the
guest's only clocksource: the time sample is not a paravirtual clock, which
[1.2 Non-Goals](1.2-non-goals.md) excludes, as it excludes a VMClock device.

The guest checks each sample's pairing against its own TSC. It reads its TSC
as `g0` immediately before the selector write and as `g1` immediately after
it, and then its realtime clock as `r`, in nanoseconds, between two more TSC
reads, whose midpoint is `c` and half distance `w`. The host reads its UTC
while it handles the write, so a sample whose `tsc` lies outside
`[g0 - p, g1 + p]`, where `p` is `pairing_ns` plus the 1 µs skew bound, in
cycles at `F`, is invalid. The kernel counts the TSC at `F_k`, in Hz, `F`
rounded down to the kHz, with its frequency correction `f`, so the guest's
realtime clock at `tsc` is `r` less `d`, the nanoseconds between `tsc` and
`c`:

```text
d       = (c - tsc) * (1 + f) * 1_000_000_000 / F_k
skew_ns = 1_000
theta   = utc_ns - (r - d)
epsilon = pairing_ns + skew_ns + w * 1_000_000_000 / F_k + |d| * 2000 ppm
```

The skew term bounds a read on another guest CPU than VP 0, whose TSC OpenVMM pairs with host
UTC. The last term bounds how far a slew below the step threshold can move the realtime clock's
rate over that time. The restore packet carries no host UTC:
repair takes a time sample instead. As Table 3.10 shows, the guest accepts a
pairing only if `epsilon` is within the bound for its use.

**Table 3.10.** Time-pairing uncertainty bounds.

| Use | Bound | Attempts | When every attempt is invalid or exceeds the bound |
| --- | --- | --- | --- |
| Restore repair | 100 µs | 3 | Repair fails, and the guest powers off |
| Initial synchronization at boot | 100 µs | 3 | Conformance fails, and the guest powers off |
| Wall-clock discipline | 100 µs | 3 | The poll is skipped; never fatal |

The guest's frequency correction runs its wall clock at host UTC's rate:

```text
f = (1 + correction) * F_k / F - 1
```

The kernel limits `f` to ±500 ppm; the guest holds a correction beyond that
limit at the limit, and reports that it did.

## 3.2.10 Guest Obligations

The guest agents perform conformance checks, watch for violations, discipline
the wall clock, and execute the snapshot time steps in every guest mode.
Production paths keep the console quiet; status goes to a state file that the
workload can read through a read-only mount. The state file reports the
outcome of each phase's checks, the declared rates, the generation, the last
downtime and its source, and the wall clock's discontinuities,
synchronization, offset, uncertainty, and frequency correction, with whether
the kernel's limit held it, and the status, correction, bounds, and
disruption counter of host UTC that the latest accepted sample published, so
that a workload can see when its host's clock is not synchronized or wanders.

**Conformance.** Before readiness, the guest only takes a time sample within
the bound, steps its clock to host UTC, and holds the frequency correction
that the sample's host clock correction gives, so the workload starts on host
time and runs at its rate. It runs every other boot check asynchronously after
readiness, starting at idle priority, so the checks never delay readiness or
take a processor from the workload. The checks cover the identity leaves and
explicit zero leaves, the CPU time bits on every CPU, the identity MSRs, the
kernel's platform, clocksource, and LAPIC-timer selection, CPU flags, tick
devices, the absence of forbidden clock parameters among those that the
kernel reads from its command line, stall-detector settings, a running
violation watcher, and kernel W+X integrity. Capture reruns the clocksource,
tick-device, and watcher checks. Restore reruns them too, checks the declared
rate in the frequency MSR again, and checks the identity leaves, the CPU time
bits, and the CPU flags of every processor that it brings online. Every check
is fail-fast: a failure powers the guest off even if the workload is running.

**Violation watcher.** The watcher follows the kernel log from before the boot
checks, so no record is missed. TSC instability; clocksource instability,
switches, or skew; TSC warps; `TSC_ADJUST` faults; RCU stalls or starvation;
soft or hard lockups; hung tasks; unchecked MSR accesses; APIC identity
mismatches; and lost log records are violations. The watcher also polls the
kernel's RCU stall count, so a stall is caught even if its record is lost. A
violation is reported as one bounded event line on the kernel log, the byte
channel, and the console, and the guest then powers off through the shutdown
port.

**Stall suppression.** Restoring after downtime makes kernel time jump, so the
guest suppresses RCU stall detection, and the debug stall detectors, before a
capture request. After restore, it releases the suppression only when the
grace period that was in flight at capture has ended, forcing a full normal
grace period first. If that grace period stays stuck beyond the stall timeout,
the guest releases the suppression anyway so that the kernel reports the real
stall.

**Wall-clock discipline.** The guest keeps its realtime clock on host UTC
through the kernel's phase-locked loop, with its frequency held: each accepted
sample sets the kernel's frequency correction from the sample's host clock
correction, which carries a restore's rate deviation, and the loop only slews
the phase, so the guest never estimates the host's rate. It polls every 16
seconds for the first four polls after boot, a restore, or a change of the
sample's disruption counter, then every 64 seconds, and takes up to three
samples per poll. An offset of at least 128 ms is stepped and counted as a
discontinuity; a smaller one is slewed. Either sets error bounds derived from
the offset and its uncertainty, to which the maximum error adds host UTC's
while the host's time service synchronizes it, which marks the clock
synchronized for applications. The kernel limits the frequency correction to
±500 ppm, of which the rate tolerance uses at most 250 ppm. The other 250 ppm
is the budget for the host's own clock correction, which the discipline
applies too, because host UTC follows the host's time service: a host whose TSC
runs more than 250 ppm from its declared rate against host UTC does not
[qualify](../ci.md#host-qualification) for the contract. A correction beyond
the kernel's limit is held at the limit and reported in the state file, so an
offset can grow until the discipline steps it. A sample whose generation
differs from the recorded one is discarded, because a
restore happened and restore repair resets the discipline. The discipline
follows host wall-clock steps and never powers off the guest. Restore repair
and the discipline step the clock through the kernel, so a workload can
observe every step through the kernel's clock-set notification, such as a
`timerfd` armed with `TFD_TIMER_CANCEL_ON_SET`.

The [snapshot protocol](5.3-snapshot-protocol.md) and
[guest repair](5.5-restore-protocol.md#557-guest-repair) define the snapshot
time steps.
